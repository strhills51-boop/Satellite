# Satellite — философия проекта

> Рабочее имя: **Satellite** (наследник ModlistTool.mo2 | Monolith).
> Этот файл — компас. Его читают первым: человек, Claude, ChatGPT, любой следующий агент.
> Если решение противоречит этому файлу, то меняется либо решение, либо (осознанно и явно) этот файл.

---

## 1. Одной фразой

**Не трогать моды руками, а работать с ними со стороны: наблюдать, понимать, описывать желаемое и применять.**
Satellite не хранит моды. Он знает о них всё, что можно знать, и направляет: что это, с чем конфликтует,
чего требует, где взять, что выбирают другие и что надо сделать, чтобы сборка стала такой, какой ты её задумал.

## 2. Откуда мы пришли

Монолит (`index.html`, ~196k строк) доказал идею и упёрся в архитектуру:

- всё в одном потоке браузера, ни одного воркера;
- каждый путь хранится строкой в IndexedDB и материализуется многократно (сотни миллионов строк в работе);
- каждая подсистема заново изобретала сверку «истина ↔ представление» со своим кешем и своей инвалидацией;
- 33 слоя стилей и сотни self-test'ов по исходникам функций.

Идеи монолита верные: пробеги, цепочки и контексты, «зубной ряд», декоративный слой поверх канона,
доноры, sync с бэкапами. **Переносим идеи, не переносим реализацию.**

Прототип **Satellite «V2 constructor core»** (`preview_40_file_windows_context_fix.html`, ~22k строк) зашёл с другой
стороны — от архитектуры. Он дал скелет, которого не было у монолита:
- машиночитаемая карта слоёв, потоков и правил + **architecture guard**, проверяющий их в рантайме;
- всё — **ресурсы** по контрактам: окна (wrapper + renderer), команды, хотки, задачи, примитивы, валидаторы, импортёры;
- **уровни доверия** (core / preset / project / external) и **политика возможностей** (по умолчанию запрещены
  запись в рантайм, хранилище, ФС, сеть, воркеры);
- **манифесты расширений** и **пресеты-композиции**: core + игра + менеджер = стек (`preset.skyrim.mo2`);
- workspace из свободных окон + **библиотека окон** с превью; **Developer Center** — фабрика расширений
  с предпросмотром, подтверждением и «контекстом для ИИ»;
- пробеги как **bucket + стадии + контракты** («факт обнаружен → ветка/эффект»);
- хранилище (`.stll`) отделено от рантайма, версии и миграции.

Его слабости зеркальны монолиту: архитектура есть, а продукта почти нет (окна конфликтов пустые), тот же
один поток и IndexedDB, а расширения исполняются в той же JS-среде — политика там держится на честном слове.

**Синтез:** UX и доменные функции — из монолита, скелет расширяемости — из прототипа Satellite,
физика (потоки, память, ярусы данных) — из нового ядра.

## 3. Направление: три слова

### Декларативно
Пользователь описывает **намерение**, а не последовательность кликов: какие моды, в каком порядке, кто кого
должен перекрывать, что считается решённым. Движок сравнивает желаемое с фактическим, строит **план** (diff),
показывает его и применяет через адаптер. Как Terraform или Nix, только для модов.

```yaml
# пример: сборка как код (формат будет уточняться)
game: skyrimse
manager: mo2
profile: Default
order:
  - separator: Textures - Landscape
    mods: [Majestic Mountains, Northern Roads, Northern Roads Patch]
rules:
  - winner: Northern Roads Patch
    over: [Northern Roads, Majestic Mountains]   # решение по цепочке
  - forbid: { family: "ENB presets", count: ">1" }
decisions:
  chains_done: [ "majestic mountains|northern roads" ]
```

### Абстрактно
Ядро не знает слов «Skyrim» и «MO2». Оно знает **сущности**: мод, артефакт (файл), маршрут (виртуальный путь),
провайдер, стек, цепочка, контекст, плагин, запись, архив, семейство, требование.
Конкретику дают **game pack** (правила игры: TES4, BSA/BA2, loose > archive, лимит 254 слота, ESL)
и **manager adapter** (как устроены MO2, Vortex, ручная установка, моды Minecraft/BG3/Cyberpunk…).
Работа с модами везде похожа, разные только форматы. Значит, общее надо вынести в ядро, а различия в паки.

### Сателлитно
Мы на орбите, а не на поверхности. Satellite:
- **не хранит и не раздаёт моды**, не перезаливает чужие файлы;
- **наблюдает**: снимает факты с диска пользователя (локально) и знание с общих источников;
- **направляет**: куда идти скачивать (Nexus, ModDB, GitHub, Mod.io…), какие версии, какие патчи, какие коллекции;
- **даёт интерфейсы**: UI, HTTP API и **MCP-сервер**, чтобы с модами могли работать и люди, и модели.

### Коллективный опыт («всеобщий бессознательный опыт»)
Каждый моддер каждый день принимает одни и те же решения: кто кого перекрывает, какой патч нужен,
что падает, что с чем не дружит. Сейчас этот опыт пропадает. Satellite собирает его **анонимно и по согласию**:
решения по цепочкам, порядок, найденные конфликты, ошибки, отзывы. Из этого строится **граф знаний о модах**:
семейства, требования, совместимости, ретекстуры и ассетные патчи, типичные порядки, рекомендации.
Отдельный пользователь получает опыт тысяч сборок, не делясь ничем, что его идентифицирует.

### Модель сервиса: каталог, а не хранилище
Как IMDb для фильмов: IMDb не хранит фильмы, но о любом фильме там есть всё и ссылки, где смотреть.
Satellite — **единая точка знания о модах**, а сами файлы живут там, где их выложил автор (Nexus, ModDB, GitHub,
Patreon, Boosty, свой сайт — бесплатно или платно, неважно). Цель: перестать бегать по всему интернету.

- **Автор — владелец своей страницы.** Он подтверждает авторство и сам публикует ссылки, версии, требования,
  известные конфликты, патчи, порядок, особенности.
- **Манифест автора** (`satellite.yaml`) — тот же декларативный формат, что и у сборок. Его можно положить
  в архив мода или в репозиторий. Локальный клиент читает его сразу, без сети.
- **У каждого утверждения есть происхождение**: «заявлено автором» / «наблюдается в N сборках» / «проверено куратором».
  Пользователь видит, кому верить.
- **Выгода всем**: пользователь получает всё в одном месте, автор получает меньше одинаковых вопросов про конфликты
  и обезличенную статистику использования мода, площадки получают трафик по ссылкам.

### Эволюция: моддинг самого Satellite
Никто не предвидит всего. Поэтому Satellite сам моддится, а его встроенные функции — это просто
**предустановленные расширения на том же API**, что доступен пользователям. Если встроенной функции API не хватает,
значит, его не хватит и сообществу: расширяем API, а не делаем обход.

Пять точек расширения, все описываются **декларативным дескриптором** (что читает, что производит, что требует):

| Тип | Что делает | Слой истины | Пример |
|---|---|---|---|
| **Анализатор** | добывает новые факты из файлов во время пробега | Факты | «найти SPID/KID ini», «распознать пресет ENB», «посчитать OAR-условия» |
| **Правило** | решает и проверяет | Намерение | теги/стикеры по условиям, «не больше одного ENB», подсказки порядка |
| **Процессор** | запускает инструмент и выпускает сгенерированный мод | Канон (через план) | Pandora/Nemesis, DynDOLOD/xLODGen, BodySlide, оптимизация текстур, скрипты xEdit |
| **Вид** | показывает | Представление | мета-блоки, счётчики, эффекты, панели |
| **Пак** | учит ядро новой игре или менеджеру | Все | game pack, manager adapter |

Основа процессоров — контракт из монолита (`deployment-processor-descriptor.v1`, Sync → Deployment processors):
входы-селекторы (расширения, префиксы путей, теги), выходы со своей ролью, **отпечаток** входов, конфигурации и версии инструмента,
исполнитель (внешний процесс / внутренний / конвейер), проверка, промоушен с бэкапом и откатом, зависимости с каскадной
инвалидацией, намерения (intent) со статусами dirty → planned → running → superseded/promoted.
По сути это **реактивная система сборки для сгенерированных модов**: поменялся вход — выход помечается грязным
и пересобирается, старые запуски не промоутятся. Эту идею переносим целиком.

Безопасность расширений:
- Код расширений работает в песочнице: модули WASM (любой язык, работают и в браузере, и нативно) с API по возможностям.
- Права объявляются в манифесте, как у браузерных расширений: читать факты, писать в представление, сеть, запуск внешних процессов.
  Пользователь видит и подтверждает. Запуск внешних процессов только в нативном клиенте.
- Писать в канон расширение не может. Оно может только предложить план, который проходит обычную проверку и бэкап.
- Схемы версионируются (`*.v1`), расширение объявляет, с какими версиями совместимо.

Петля эволюции: пользователь пишет расширение → делится в каталоге → популярные становятся встроенными.
Обезличенная статистика о том, какие расширения и конвейеры инструментов применяют, — тоже часть датасета
**паттернов моддинга** (например, типичная цепочка xLODGen → DynDOLOD → Pandora → BodySlide).

## 4. Слои истины (главный закон)

Корень проблем монолита — смешанная истина. Здесь слои разделены жёстко:

| Слой | Что это | Кто пишет | Пример |
|---|---|---|---|
| **Факты** | то, что наблюдается и проверяемо | только сканеры | файлы, размеры, TES4-заголовок, VRAM DDS, стек провайдеров |
| **Канон** | состояние менеджера модов | только адаптер (чтение/commit) | modlist.txt, plugins.txt, папки |
| **Намерение** | чего хочет пользователь | пользователь | желаемый порядок, правила, «цепочка решена» |
| **Знание** | агрегированный опыт сообщества | Satellite-сервис | «этот патч обычно ставят после X», семейство, требования |
| **Представление** | как это выглядит | UI | цвета, эмодзи, теги, декорации, мета-блоки |

Правила:
1. Нижний слой никогда не пишет в верхний, представление никогда не меняет факты и канон.
2. Всё производное **вычисляется** из слоёв, а не хранится рядом «на всякий случай».
3. Одна инвалидация на весь движок: граф зависимостей. Изменилось X — пересчиталось ровно то, что от X зависит.
4. Канон меняется только через **план → проверка → бэкап → commit**. Никаких тихих записей в папки MO2.

## 5. Инженерные принципы

### Реактивность
- **UI = f(state).** Один store на сервере, UI получает проекции и события. Ни одного «кеша для этой панели».
- Каждая производная проекция объявляет свои зависимости. Пересчёт ленивый, отменяемый, с поколением (generation).

### Данные: горячие, тёплые, холодные
| Ярус | Где | Что | Бюджет |
|---|---|---|---|
| **Горячий** | RAM движка | порядок, приоритеты, стеки, статистика W/L/M/X, текущий контекст | мгновенный доступ, < 200 мс на пересчёт |
| **Тёплый** | RAM, колонки/индексы | таблица провайдеров, интернированные пути, CSR-индексы | целые числа, без строк на путь |
| **Холодный** | диск (`<profile>/monolith/`) | сканы по сигнатурам, снапшоты, журналы, версии | грузится по требованию, страницами |

Каждая новая фича в описании явно указывает, в каком ярусе живут её данные и сколько их.

### Многопоточность
- Обход диска, разбор форматов, анализаторы работают в пуле воркеров. Параллельно по умолчанию, последовательно только по необходимости.
- Любая долгая операция — **job**: прогресс, отмена, поколение, лог. UI не блокируется никогда.

### Память
- Путь = `uint32`, мод = `uint32`. Строки хранятся один раз в интернере.
- Колонки вместо объектов, CSR вместо вложенных списков.
- Ничего не материализуется целиком: списки файлов только страницами, UI видит только видимое (виртуализация).
- Бюджет на сборку в 10 млн файлов: ≤ 1,5 ГБ RAM.

### Чистая архитектура
```
          ┌────────────── UI (web) ──────────────┐   MCP / HTTP API
          │                                      │         │
   ┌──────▼──────────────────────────────────────▼─────────▼──────┐
   │ Application: команды, планы, jobs, проекции, события          │
   ├───────────────────────────────────────────────────────────────┤
   │ Domain (ядро): сущности, слои истины, граф зависимостей,      │
   │ VFS, стеки/цепочки/контексты, правила, diff — БЕЗ ввода-вывода│
   ├───────────────────────────────────────────────────────────────┤
   │ Ports  →  Adapters:                                            │
   │   game packs (skyrimse, fo4, …)  manager adapters (mo2, vortex)│
   │   formats (tes4, bsa, ba2, dds, nif…)  storage (cold tier)    │
   │   knowledge source (Satellite service, Nexus API…)            │
   └───────────────────────────────────────────────────────────────┘
```
- Ядро не импортирует адаптеры. Адаптеры заменяемы. Каждый порт тестируется на синтетике.
- Каждое правило игры живёт в game pack, а не в `if game == skyrim` посреди ядра.

### Семантический слой (карта для агентов)
Корень беды монолита — не размер, а **переопределения**: `parseModlist`, `serializeModlist` и десятки других
функций подменены поверх себя по нескольку раз (`__orig…`, «теневые» версии, owners V527). Каждый новый слой
не знал, что такое уже есть, и писал своё рядом. Поэтому кроме самих файлов проект ведёт **семантический слой** —
файлы для агента, а не для компилятора:
- `docs/semantic/MAP.md` — **понятие → единственный владелец** (файл, тип, функция) и «не путать с»;
  указатели по файлам: что в файле, какие в нём блоки.
- `docs/semantic/monolith/` — конспект монолита: где что лежит в 196 тыс. строк, какие версии чего живы, какие
  мертвы, что чем переопределено.
- Правила: перед новой функцией — найти понятие в карте; есть владелец — расширяй его, а не пиши рядом;
  нет — добавь строку в том же коммите. Переопределять функцию поверх существующей (обёртка «старое + новое»)
  запрещено: меняем владельца, а историю хранит git.
- CI проверяет, что каждый исходник упомянут в карте и каждая ссылка карты существует (`tools/check-map.sh`).

### Интерфейс
- **Сначала один в один с монолитом**: вид, плотность, блоки, модалки, жесты. Потом решаем, что менять.
- Скорость интерфейса — часть дизайна: 60 fps при прокрутке, реакция на действие < 100 мс.
- Внутренняя диагностика доступна, но живёт в отдельном режиме (debug), а не в рабочем экране.

### Этика и право
- Никаких модов на наших серверах. Только ссылки, метаданные и атрибуция авторов.
- Телеметрия только **opt-in**, анонимная, с понятным списком того, что отправляется; локальная работа полностью без сети.
- Уважать правила источников (Nexus API ToS, лимиты, авторские права). GDPR как минимум.

## 6. Бюджеты производительности (проверяются бенчмарками)

- [ ] Пересчёт стеков/цепочек после перемещения мода: < 200 мс на 5 000 модов / 10 млн провайдеров
- [ ] Старт из кеша: < 10 с на 3 млн файлов
- [ ] Холодный пробег: ограничен диском, CPU не узкое место
- [ ] RAM: ≤ 1,5 ГБ на 10 млн провайдеров
- [ ] Любой ответ API для UI: < 50 мс (кроме поиска по VFS: < 300 мс)
- [ ] Таблица «зубной ряд»: плавная на 500 модов × 50 000 столбцов (виртуализация по двум осям)

## 7. Словарь (из монолита)

- **Пробег** — анализ сборки. **Поверхность** — дешёвые сигнатуры. **Бездна** — полный обход.
- **Провайдер** — мод (или архив мода), который даёт файл по виртуальному пути.
- **Стек** — провайдеры одного пути по приоритету. **Цепочка (exact chain)** — пути с одинаковым стеком модов.
- **Контекст** — связная компонента модов через цепочки. **Зубной ряд** — матрица мод × файл (выигрывает/проигрывает).
- **W/L/M/X** — выигрывает / проигрывает / в середине стека / полностью перекрыт; **+n** — уникальные файлы.
- **Представитель разделителя** — строка разделителя в списке модов. **Функциональные разделители** — SYNC, Overwrite, Skyrim.
- **Донор** — внешняя сборка, из которой переносят моды. **Sync/commit** — запись изменений в MO2 через план и бэкап.
- **Мета-блоки (meta stack)** — перетаскиваемые блоки сводки. **Hover-облачко** — поповер мода при наведении.

## 9. Правила работы для агентов (Claude, ChatGPT, …)

1. Сначала прочитай этот файл (лежит в корне репозитория), затем `docs/semantic/MAP.md`, `docs/adr/`, активную дистанцию в `docs/distances/` и `docs/UI-PARITY.md`.
2. Каждая задача ссылается на пункт дорожной карты; по завершении отметь чекбокс в том же коммите.
3. Новая фича описывает: слой истины, ярус данных, объём, зависимости проекций, поведение при отмене.
4. Запрещено: второй владелец понятия (см. `docs/semantic/MAP.md`), переопределение функции поверх существующей, второй источник истины, кеш «для одной панели», запись в папки MO2 мимо плана и бэкапа, строка на каждый путь.
5. Перед UI-работой сверяйся со скриншотами монолита (паритет один в один, пока не решено иное).
6. Изменения производительности подтверждаются бенчмарком до/после.
7. Если хочется нарушить принцип отсюда — сначала предложи правку этого файла.
8. Крупная задача оформляется как **дистанция** (протокол из VIBE-сессий): цель, **контракт закрытия**
   (что должно быть наблюдаемо истинно, чтобы считать её сделанной), решения с причинами, находки и риски,
   следующий фокус. Закрытие только по фактам (тест, бенчмарк, скриншот), а не по ощущению.
9. Паритет с монолитом доказывается **наблюдаемым поведением** (скриншоты, сценарии Playwright, данные API),
   а не построчной эквивалентностью исходников.
