## 4. Для NG

### Перемещение модов (ядро, переносить точно)
- Единственный путь мутации порядка: `commitModlistMoveFromAnyContext({modIds, targetSeparatorId, targetModId, before})` → `reorderMods`. Порядок цепочки конфликтов — **производный** от modlist; никаких локальных «display order» (заглушки 83481–83491 и сброс `conflictChainOrderOverrides` это подтверждают).
- Алгоритм применения (`applyModlistReorderOperationV496`, он же no-op-симуляция `isModlistMoveNoop`): вынуть все `modIds` из всех разделителей в порядке обхода (порядок перемещаемых = их текущий порядок в modlist, а не порядок в `modIds`); индекс вставки = позиция `targetModId` в **уже очищенной** цели (не найден → конец), `before=false` → +1, clamp; вставить блоком. No-op = отпечаток раскладки не изменился. Отказ: цель — системный/заблокированный разделитель, `targetModId ∈ modIds`, `canMoveModIdsToTarget` = false.
- Drop на LG-композит: якорь = первый член (before) или последний (after), drop внутрь своей LG запрещён. После — валидация `LogicalGroupNGSourceOperationAuthorityV567.validate` (только лог, без отката — в NG сделать транзакционно).
- before/after: горизонтальная ориентация → по X середине, иначе по Y (`getDropListOrientation` правила в §2 85127).

### Дельта-сохранение порядка (v496)
- Операция `{id, at, modIds[], targetSeparatorId, targetModId, before, reason}`; патч `modlist_reorder_ops` с `operations[]`, одной записью журнала (`reorder_mods`, coalesced) и опциональным `syncRecord`. Коалесценция: только **соседние** операции с одинаковым множеством `modIds` — последняя побеждает. Переигрывание при загрузке — последовательно. После закрытия модалки — материализация полного порядка (`modlist_order_state`). Для NG: журнал операций порядка + периодический снимок — та же модель; телефонные пачки не создают sync-запись.
- Тайминги (для паритета ощущений): flush 260 мс + idle 1100; материализация 320 + idle 1800; зеркало автосейва 180 + idle 1200; pagehide — принудительный flush.

### Каноническая проекция цепочки (v490) — формулы
- Ось файлов: `chain.files → group.paths → group.files → fileStacks.files → samplePaths`, без пересортировки, уник. по нормализованному пути.
- Владельцы файла: из стека (первый источник стека для пути побеждает), иначе участники с путём в owned/wins/loses; сорт. по глобальному приоритету мода (`getGlobalPriorityByModName`), затем имя.
- Победитель файла: объявленный в стеке (если среди владельцев) → единственный явный `wins` → нет. Клетка участника: не владелец → `missing`; есть победитель → `win|lose`; иначе по явным спискам; оба/ни одного → `unknown`.
- Legacy-победитель цепочки/пути (`getConflictPathWinnerNameForGroup`, `refreshConflictPresentationDetailOrderV703`): **последний включённый** участник в порядке modlist, иначе последний. В MO2 это и есть правило (ниже по списку = выше приоритет).
- Мульти-цепочка для дерева (`conflict-tree-all-chains-v533`): объединение по пути; путь без доказательств владения сохраняется; primary = первая цепочка по порядку групп.
- Хэш: FNV-1a 32 (offset 0x811c9dc5, prime 0x01000193) с разделителем 0xff после каждой части; hex(8). Используется как ключ кэша (`runtimeStamp`) и подпись (`signature`).
- «Зубы»: 1 файл = 1 сегмент, строка состояний `w/l/u/m` (+`r` для линейки); цвета §2 86866.

### Фокус конфликтов (состояние UI)
- Каноническая форма `conflictFocus = {chainKey, modName, filePath, fileIndex, presentationEntityKey, presentationMembershipFingerprint, presentationContextId, revision}`; legacy-зеркало `selectedGroupKey/selectedModName`. Смена цепочки сбрасывает файл; presentation-поля сохраняются, только если тот же membershipFingerprint содержит новую backend-цепочку. Разрешение группы для фокуса: membership → entityKey → backend chainKey. В NG — одна шина событий фокуса вместо трёх обёрток и двух MutationObserver на весь документ.

### Декорации (схема для `sat-core::canon` / UI)
- Схема `visual` — `sanitizeModVisual` (§2 88821) с диапазонами и умолчаниями; хранить только отличия. Разделитель — без width/height/margins. Встроенные системные визуалы — таблица §2 91055; для system/locked пользовательский визуал игнорируется.

### Вероятные ошибки / спорные места
1. `buildSelectedSummary` живая версия (135303) не возвращает `stickers` и считает теги по `derived.tags`, базовая — по `getModTags` + стикеры. Если какой-то блок сводки читает `data.stickers`, он пуст после override.

5. В `setSelected{Mod,Separator}DecorationField` пустой цвет не удаляет ключ; borderRadius в UI по умолчанию показывает 14, хотя данных нет.
6. `sanitizeSeparatorVisual` пропускает `lineBreakBefore/After/fullWidth` в визуал разделителя (бессмысленные для него поля).
7. Два `MutationObserver` (`subtree:true` на `documentElement`) — CP4 гидратирует каждый добавленный узел, CP5 планирует полную DOM-синхронизацию фокуса на каждое добавление: заметная стоимость на больших списках.

9. `normalizeDecorEmoji` режет до 4 code point — сложные ZWJ-эмодзи (семьи, флаги с модификаторами) ломаются.
10. `getConflictGroupFilePaths` 88068 — мёртвый дубль 143199 (разные источники путей и нормализация: `normalizeTreeConflictPath` vs `normalizeConflictIgnorePath`). Не переносить 88068.
