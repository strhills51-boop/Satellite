- **Resource** `modlisttool.process-resource-contract.v3`: `schema, resourceId (CONTRACT_ID_RE /^[a-z0-9][a-z0-9._:-]{0,255}$/i), resourceKind (req), locator (string|object), role (source|target|staging|internal|verification|backup), expectedRevision (string|null), requiredAccess[] (⊆ ALL_ACCESS, lower), providerId (req, RE), metadata{}`. Запрещено `grantedAccess` (в корне и в metadata).
- **Effect** `modlisttool.process-effect-contract.v3`: `schema, effectId, stageId, operation (∈ OPERATION_POLICIES), sourceResourceIds[], targetResourceId, destructive, requiresBackup, backupResourceId, expectedTargetRevision, rollbackPolicy ('none' по умолч.; встречаются restore-backup, reverse-operation, restore-snapshot, discard-staging), verificationPolicy, payloadRef, stagingRef, metadata{sequence, dependsOnEffectIds[] …}`.
- **OPERATION_POLICIES** (178 801): `inspect[inspect]`, `enumerate[enumerate]`, `read[read]`, `materialize[read,materialize]`, `execute[execute]`, `create[create,write]`, `write[write]`, `append[append,write]`, `replace[replace,write]` **destructive**, `move` source[read,move] target[create,write,move] **destructive**, `delete[delete]` **destructive**, `verify[read,verify]`, `promote[promote]`.
- Правила: payload обязателен для materialize/execute/create/write/append/replace/move/delete/promote; destructive ⇒ явный `destructive:true` + `requiresBackup:true` + rollback≠none; requiresBackup ⇒ backupResourceId или rollback reverse-operation/restore-snapshot.
- **Компиляция**: Кан по `dependsOnEffectIds` (старт по `sequence`); эффект блокируется, если зависимость заблокирована; иначе барьеры по **проецированному** состоянию; после компиляции — identity-проекция (create/write/append/replace/promote/materialize → все ресурсы той же identity `ready`; move → источник `unavailable`; delete → target `unavailable`). Блокеры сворачиваются в root blockers. Итог `ready|blocked`.
- Kernel-маршрут dry-run: capability → barrier → verification → promotion; барьерные факты ядра — 13 (см. 182 566).

### 4.3 Deployment state (`project.deployments`, `modlisttool.deployments-state.v1`)
`{schema, version:1, revision, intents[] (≤512, уникальны по identityKey), resolvedHistory[] (≤200), processorSettings{ [processorId]: {enabled?:bool, configuration?:{}} }, updatedAt}`.

**Intent** `modlisttool.deployment-intent.v1` (строгие ключи): `schema, intentId ('deployment:<proc>:<profile>:<target>'), identityKey ('<proc>::<profile>::<target>'), processorId, profileId, targetId, status, desiredFingerprint, deployedFingerprint, outputState (present|missing|unknown|invalid), causes[] (≤128), sourceFactIds[] (≤512), activeRunId, activeRunFingerprint, lastSuccessfulRunId, lastRunId, lastRunDisposition, blockedBy[], ignoreUntilFingerprintChanges, supersededByFingerprint, createdAt, updatedAt, invalidatedAt, resolvedAt, revision, metadata{fingerprintKind ('provisional-change-fact-chain'|'canonical-input-state'), descriptorDigest, fingerprintSchema, fingerprintEnvelopeDigest, fingerprintReady, fingerprintBlockers[], dependencyDigest, stateDisposition, reuseArtifactId}}`.
Инварианты: ids `/^[a-z0-9][a-z0-9._:-]{0,191}$/` (**lower-case** — profileId должен быть id, не имя профиля MO2); fingerprint `/^(?:sha256:)?[a-z0-9][a-z0-9._:-]{2,255}$/i`; desired обязателен кроме clean/ignored; clean ⇒ desired==deployed; `queued|running|verifying|promoting|superseded` ⇒ activeRunId.

**Cause**: `causeId, code (UPPER), source, entityType, entityId, resourceId, message, detail, firstSeenAt, lastSeenAt, count`; слияние по causeId (count суммируется).

**Машина intent (INTENT_TRANSITIONS, 183 595)**:
```
clean      → dirty | stale | blocked | ignored
dirty      → planned | blocked | ignored | stale
blocked    → dirty | planned | ignored | cancelled
planned    → queued | dirty | blocked | cancelled | superseded
queued     → running | cancelled | failed | superseded
running    → verifying | failed | cancelled | superseded
verifying  → promoting | failed | cancelled | superseded
promoting  → clean | failed | superseded
failed     → dirty | planned | ignored | cancelled
stale      → dirty | planned | blocked | ignored
superseded → dirty | failed | cancelled
cancelled  → dirty | planned | ignored
ignored    → dirty | stale | clean
```
(переход в тот же статус разрешён). Обходят таблицу: `upsertIntent`, `settleRun`, `patchIntentEvaluation` (CP4).

**Машина run (RUN_TRANSITIONS, 183 611)**: `created→planned|cancelled; planned→queued|cancelled|superseded; queued→running|cancelled|failed|superseded; running→verifying|failed|cancelled|superseded; verifying→promoting|failed|cancelled|superseded; promoting→succeeded|failed|superseded`; терминальные `succeeded, failed, superseded, cancelled`. CP6-ledger использует урезанную таблицу (verifying — тупик до CP7).

**upsertIntent (инвалидация)**: нет intent → создать со статусом `stale` (если outputState missing) иначе `dirty`. Есть → desired:=новый, causes merge, sourceFactIds union, invalidatedAt/updatedAt:=at, resolvedAt:=null, revision+1; затем, если НЕ (ignored ∧ ignoreUntilFingerprintChanges ∧ fp не изменился): (активен ∧ fp изменился) → `superseded` (+supersededByFingerprint, disposition `active-run-superseded-by-invalidation`, activeRunId сохраняется); иначе outputState missing → `stale`; иначе (clean ∧ fp тот же ∧ deployed==desired) → `clean`; иначе не активен → `dirty`; активен ∧ fp тот же → статус не меняется.

**beginRun**: fp run == desired (иначе `DEPLOYMENT_PLAN_STALE`) → `queued` + activeRunId/activeRunFingerprint/lastRunId, disposition `queued`.

**settleRun(outcome.status)**: promotable = succeeded ∧ runFp==desired ∧ status≠superseded.
- succeeded ∧ promotable → `clean`, deployed:=runFp, lastSuccessfulRunId, resolvedAt, копия в resolvedHistory, disposition `succeeded-and-current`;
- succeeded ∧ runFp≠desired → `dirty`, lastSuccessfulRunId:=run, deployed **не** меняется, `succeeded-but-superseded`;
- cancelled → `cancelled`; superseded → `dirty`; прочее/неизвестное → `failed`.
Всегда activeRunId:=null, activeRunFingerprint:='', supersededByFingerprint:=''. `DEPLOYMENT_RUN_ID_MISMATCH` — только issue (state всё равно меняется, ok=false).

### 4.6 Fingerprint (CP4) — что входит
Конверт `deployment-fingerprint-envelope.v1` (sha256 от stableStringify): `{schema, algorithm:'sha256', normalizationVersion, policyId, processorId, profileId, targetId, processor: includeProcessorVersion ? {descriptorVersion, implementationVersion, descriptorDigest} : null, configuration: includeConfiguration ? {schemaId, version, value: deepMerge(defaults, configured)} : null, tool: includeToolVersion ? toolIdentity{schema,toolId,adapterId,state,version,executableDigest,installationRevision,configurationDigest,metadata} : null, selectors[{selectorId,resourceKind,revisionPolicy,fingerprintRole,required,cardinality,included,count,contributions[]}], dependencies: includeDependencies ? contributions[] : []}`.
`included` = role include, или conditional при ≥1 входе; exclude не входит. Входы селектора сортируются по `identity:resourceId`.
Вклад входа по revisionPolicy (всегда `resourceId, resourceKind, state`): identity → `identity`; content → `identity, contentDigest||revision`; metadata → `identity, metadataDigest||sha256(metadata)`; project → `identity, projectRevision||revision`; tool → `identity, toolVersion||revision`; composite → `identity, revision, contentDigest, metadataDigest, projectRevision, toolVersion`.
Input snapshot `deployment-input-snapshot.v1`: `schema, selectorId, resourceKind, resourceId, identity, state (ready|missing|stale|unavailable|denied|error), revision, contentDigest, metadataDigest, projectRevision, toolVersion, tags[], extensions[], paths[], metadata{}`.
Dependency artifact `deployment-dependency-artifact.v1`: `schema, artifactId, processorId, profileId, targetId, artifactKind, fingerprint, revision, state, verificationStatus, promotionStatus, createdAt, promotedAt, metadata`. Output snapshot: `schema, targetId, state, deployedFingerprint, revision, artifactId, verificationStatus, metadata`.

**evaluateState — решающая таблица (по порядку):**
1. активен ∧ activeRunFingerprint ≠ fp → `superseded` / `active-run-superseded`;
2. активен → текущий статус / `active-run-current`;
3. ignored ∧ ignoreUntil… ∧ desired==fp → `ignored` / `ignored-until-change`;
4. есть блокеры fingerprint'а → `blocked` / `inputs-blocked`;
5. output missing|invalid → `stale` / `output-missing|output-invalid`;
6. output present ∧ deployed==fp ∧ (verification не обязательна ∨ output.verificationStatus=passed) → `clean` / `up-to-date`;
7. есть reuse-кандидат → `dirty` / `reuse-available`;
8. иначе `dirty` / `rebuild-required`.

### 4.7 Deployment plan `modlisttool.deployment-plan.v1` (строгие ключи)
`schema, version:1, planId ('deployment-plan:'+sha[:32]), planDigest, processorId, profileId, targetId, descriptorDigest, descriptorVersion, implementationVersion, expectedFingerprint, mode (build|reuse|noop), status (ready|blocked|noop), stale, runnable, physicalMutation:false, physicalBoundary:'deployment-executor', resourceGraph{schema:'…resource-graph.v1',resources}, effectGraph{schema:'…effect-graph.v1',effects}, resources, effects, stages[{stageId,title,order}], policies{executor,verification,promotion}, blockers, warnings, summary{resources,effects,stages,inputs,dependencies,mode}, metadata{intentId,intentRevision,outputTarget,fingerprintEnvelopeDigest,providerId,compileOnly}, createdAt`. Digest = sha256 всего, кроме planId/planDigest/status/stale/runnable/physical*/summary/metadata/warnings/createdAt (блокеры входят как `{code,path,detail,severity}`).

**Ресурсы (всегда)**: `input:*` (source, inspect/read/verify, по одному на вклад селектора), `configuration` (source, rev = sha256(envelope.configuration)), `tool` (если executor не none/composite; source, read+execute), `dependency:*` (source), `output` (target, identity `<p>:<prof>:<t>:production`, rev = deployedFingerprint), `backup` (backup), `provenance` (target).
**build** доп. ресурсы (пары target/source-alias с общей identity `<p>:<prof>:<t>:staging:<fp>[:suffix]`): staging, materialized-config, execution-receipt (internal), verification (verification).
**build эффекты (10, по порядку sequence)**:
1 `prepare-staging` create→staging-target (discard-staging);
2 `materialize-config` write [configuration, staging-source]→config-target, dep 1;
3 `launch-process` **execute** [inputs, deps, config-source, staging-source, tool]→receipt-target, payload `deployment-execution-envelope{processorId,profileId,targetId,fingerprint,executor,stagingResourceId}`, dep 1,2;
4 `capture-output` write [staging-source, tool]→receipt-target (stdout/stderr/exitCode/progress), dep 3;
5 `verify-process` verify→receipt-source (`process-exit-success`), dep 4;
6 `verify-output` verify [receipt-source]→staging-source (verificationPolicy дескриптора), dep 4,5;
7 `publish-verification` write→verification-target, dep 5,6;
8 `backup-current-output` create→backup (reverse-operation, `optionalWhenMissing`), dep 7;
9 `promote-output` **replace** [staging-source, verification-source]→output, destructive, requiresBackup, backup, `expectedTargetRevision=deployedFingerprint`, `restore-backup`, post-promotion verification, dep 7,8;
10 `publish-provenance` write [output, verification-source, receipt-source]→provenance, dep 9.
**reuse** (4): verify-reuse-artifact → backup-current-output → `promote-reuse-artifact` (replace из reuse-artifact) → publish-provenance. **noop**: эффектов нет.
Конвейер: `build` → `validatePlan` → `compilePlan` (v526 compileEffects, ctx `deploymentPlanCompile:true`) → `authorizeRun` → CP6 `createEnvelope` → `executor.start`.

### 4.9 Спорные места и вероятные ошибки
1. **183 731 `normalizeCause`**: `digest(...).slice(10)` отрезает префикс `fnv1a32:` (8) **и 2 hex** → causeId из 6 hex (24 бита), рост коллизий. В CP3/CP4 `causeFromFact` — `slice(0,32)` (полный digest). Несогласованно.
2. **FNV-1a 32** для `descriptorDigest`, registry digest, causeId, factDigest — не крипто, 32 бита; при этом descriptorDigest входит в sha256-конверт и в план. В NG — везде sha256.
3. **`settleRun`** (184 072) не проверяет таблицу переходов; случай A→B→A (supersede, затем вход вернулся к A): status `superseded`, runFp==desired ⇒ не promotable ⇒ падает в ветку `failed`, хотя run успешен и актуален.
4. **`patchIntentEvaluation`** (186 853) пишет статус напрямую и не увеличивает `intent.revision`/`state.revision` (в отличие от upsert/transition) — ломает оптимистичную конкуренцию по revision.
5. `beginRun` 184 060: мёртвый тернарник `planned?'queued':'queued'`.
6. `selectorMatch` pathPrefixes без границы сегмента (`meshes/actors` ⊂ `meshes/actorsx`). Две разные нормализации путей (CP3 `normalizePath` vs CP4 input snapshot).
7. Несогласованность `ID_PATTERN`: CP1–CP3/CP6 lower-case, v526/CP4/CP5 `/i`. ProfileId из имени профиля MO2 с заглавными упадёт в `buildIntentIdentity`.
8. Провайдер плана CP5 (187 483) выдаёт доступ из `metadata.compileGrantedAccess` контракта — обход принципа «гранты только от провайдера» v526 (ловится лишь ключ `grantedAccess`).
9. CP6 188 529: проверка `… && false` — мёртвая (заменена следующей проверкой production-output).
10. `upsertIntent` обновляет `metadata` только при создании; при апдейте CP3-провизорный `descriptorDigest` устаревает (CP4 патчит).
11. `resolveProfileIds` без профиля → blocker ⇒ атомарный батч целиком не применяется из-за одного факта.
12. v526 `buildKernelFacts`: SOURCE_* и TARGET_* выводятся из одних и тех же kind'ов — сторона не различается.
13. Gauntlet CP2 `validate()` гоняет весь каталог (46 сценариев + adaptPlan) при каждой загрузке страницы — лишняя нагрузка старта.
14. Манифесты: CP1 `addedGlobals` называет `ModlistToolSyncDeploymentSurfaceV527` (реально `…CP1`), CP3 — `…RouterV527` (реально `…CP3`), CP4 — `…RouterV527CP3` (реально публикует `…RouterV527`). Манифесты v6 Gauntlet CP2 — замороженный объект без присваивания.
15. In-memory FS (182 825): `write({type:'write',position})` игнорирует position/seek/truncate — тесты не ловят позиционную запись.
16. `computeFingerprint`: `envelopeDigest` == `fingerprint` (дубль); fingerprint считается и при блокерах — потребители обязаны смотреть `ready`.
