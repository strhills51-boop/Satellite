## 1. Обзор
Сегмент — хвост файла, три независимых слоя:
1. **v527 Deployment CP6-хвост → CP9** (188 828–191 028): исполнитель escort-процесса заканчивает прогон в `verifying` (никогда `clean`) и пишет receipt; CP7 — транзакция staging → verification → backup → promote → post-verify → rollback; CP8 — первый «production»-процессор `deploy.animation-behavior` (Pandora/Nemesis) с реестром движков, подготовкой envelope, инспекцией логов и выхода; CP9 — панель «Deployment processors» внутри SYNC-модалки. Всё — **контракты и самотесты без физического мира**: глобально не зарегистрированы ни транспорт, ни promotion-адаптер, ни store, ни UI-handler'ы; CP10 («Processor Gauntlet») в файле отсутствует. Через флаги-прелюдии (`__MODLISTTOOL_PHONE_CP3_PRESENT__/CP10_ACTIVE__/CP9_ACTIVE__`) **жесты CP2, весь CP3 и весь CP6 мертвы**; живы: макет CP2 (вертикальный стек 3 панелей, ☰-меню, гаттеры), CP23 (запрет нативного DnD), **CP9-контроллер (итог CP17–CP23: tap / double-tap / tap→hold / hold-drag / ручной скролл) поверх `ModlistToolPhoneBridgeV2` (26 961)**, CP14 (дебаунс ввода). ## 4. Для NG

### 4.1 Execution receipt `modlisttool.deployment-execution-receipt.v1` (CP6, 188 899)
`schema, version:1, receiptId:'deployment-receipt:<runId>', runId, planId, planDigest, processorId, profileId, targetId, fingerprint, status ∈ {verifying, superseded, failed, cancelled}, process{exitCode, signal, transportId, transportSessionId}, progress, stdout[], stderr[] (строки {sequence?, at?, line}), warnings[], errors[{code,message,at}], executionCompleted (verifying|superseded), verificationRequired (verifying), promotable:false, stagingOnly:true, productionMutation:false, promotionInvoked:false, physicalSyncBoundaryInvoked:false, envelopeDigest, completedAt, metadata (от транспорта)`.
Коды отказов: `PROCESS_EXIT_NONZERO`, `EXECUTION_CANCELLED`, `HEARTBEAT_TIMEOUT`, `EXECUTION_TIMEOUT`, `TRANSPORT_EXECUTION_FAILED` (или `error.code`), предупреждение `PROGRESS_REGRESSION_IGNORED`; блок до транспорта — `REQUEST_BLOCKED`.
**Автомат исполнителя** (run ledger): `… → running → {verifying | superseded | cancelled | failed}`; intent: success ∧ fp==desired → `verifying`; success ∧ fp≠desired → `superseded`→settle→`dirty` (deployed не меняется); failed/cancelled → settleRun(status).
Транспорт-контракт: `{transportId, kind?, family?, start({envelope, emit, signal}) → {sessionId, exitCode, signal, metadata}}`; события `emit({type: accepted|started|heartbeat|progress|stdout|stderr|exit|error|cancelled, message, value, label, data})`; heartbeat-таймер и общий timeout через AbortController.

### 4.2 Promotion transaction (CP7)
Предусловия (`validateTransactionRequest`): receipt.status=`verifying`; verification.ok ∧ report.status=`passed`; artifact.fp = intent.desiredFingerprint; receipt.fp = artifact.fp; intent.activeRunId (если есть) = receipt.runId; adapterId. Иначе `status:'blocked'`, адаптер не вызывается.
Адаптер: `{adapterId, backup(ctx)→{ok, backupId, hadPrevious}, promote(ctx+backup)→{ok, promotionId, productionMutation, productionDigest}, verifyProduction(ctx+promotion)→{ok, productionDigest}, rollback(ctx+backup+promotion+reason)→{ok, restored}}`, ctx = `{transactionId, intent, artifact, signal}`.
Автомат: `running → backup → promote → post-verify → succeeded`; любой сбой → `failure` → (если есть backupId) `rollback` → `rolled-back` (rollback ok) | `failed`. Коды: `PROMOTION_BACKUP_FAILED`, `PROMOTION_APPLY_FAILED`, `POST_PROMOTION_VERIFICATION_FAILED`, `PROMOTION_TRANSACTION_FAILED`.
Выходы: `transaction.v1 {transactionId ('deployment-promotion:<runId>'), status, artifactId, verificationReportId, promotionReceiptId, rollbackManifestId, startedAt, finishedAt}`; `promotion-receipt.v1 {promotionReceiptId, transactionId, runId, planId, processorId, profileId, targetId, fingerprint, status, backup, promotion, postVerification, rollbackManifestId, productionMutation, promotionInvoked:true, startedAt, finishedAt, log[{stage,ok,detail,at}], digest}`; `rollback-manifest.v1 {rollbackId:'rollback:<tx>', transactionId, backupId, promotionId, required, status: completed|not-required|failed, reason, detail, createdAt, digest}`. После: settleRun(`succeeded`) → intent `clean`, deployedFingerprint=fp; иначе settleRun(`failed`).
Artifact manifest `deployment-artifact-manifest.v1`: `artifactId, runId, planId, planDigest, processorId, profileId, targetId, fingerprint, stagingResourceId, state('staged'), files[{path,size,digest sha256,kind}], summary{fileCount,totalBytes,treeDigest = sha256(stable(files sorted by path))}, createdAt, metadata`. Verification report `deployment-verification-report.v1`: `reportId:'deployment-verification:<artifactId>', artifactId, runId, fingerprint, status passed|failed, checks[{name,pass,required,detail}], verifiedAt, reportDigest`.

### 4.5 Гейтинг действий `deriveActions` (190 424)
- `inspect` — всегда.
- `plan` — ¬runActive ∧ fingerprintReady ∧ ¬blockers ∧ status ∉ {clean, ignored}.
- `run` — ¬runActive ∧ planCurrent ∧ authorized ∧ status ∈ {planned, queued, dirty, stale, failed, cancelled}; authorized = `authorization.authorized` ∨ `compileReport.status==='ready'`.
- `cancel` — runActive (run.status ∈ ACTIVE_RUN_STATUSES).
- `retry` — ¬runActive ∧ status ∈ {failed, cancelled}.
- `reuse` — ¬runActive ∧ (disposition `reuse-available` ∨ reuseArtifactId) ∧ ¬blockers.
- `ignore-until-changed` — ¬runActive ∧ status ∉ {clean, ignored}.
- **Нет `mark-clean`**: clean только через promotion-транзакцию. Команда несёт stale-guard `expectedFingerprint, planId, planDigest, runId`.

### 4.6 Вероятные ошибки / спорное (deployment)
1. **`planCurrent` (190 428) сравнивает `plan.desiredFingerprint || plan.fingerprint`**, а у реального плана CP5 поле `expectedFingerprint` (187 829/187 854) → для настоящих планов **Run никогда не включится**; самотест проходит только из-за фикстуры с `desiredFingerprint`. Аналогично `compileReport.status==='ready'` vs реальный `compileReport.ready` (boolean, см. CP8 самотест 190 104).
2. **CP7 не трогает run ledger CP6**: после promotion run остаётся `verifying` (ACTIVE) → CP9 показывает активный прогон, `Cancel` включён, `running`-счётчик врёт; `run.status` никогда не станет `succeeded/promoting`.
3. CP6 188 841: отсутствие `exitCode` у транспорта = 0 (успех). CP8 `process-exit-success` тоже `exitCode ?? 0`.
4. CP7 `validateTransactionRequest` доверяет переданному `verification` (не перепроверяет `reportDigest`, не нормализует receipt) — подделанный `{ok:true, report:{status:'passed'}}` проходит. Нет CAS `expectedTargetRevision = deployedFingerprint` (план CP5 эффект 9 его требует) — ни транзакция, ни адаптер его не получают. `request.signal` не проверяется между стадиями.
5. При сбое **до** promote (backup ok) всё равно зовётся rollback; при сбое backup — статус `failed` без rollback, `rollbackManifest.status='failed'` хотя откатывать нечего.
6. CP8 процессор зарегистрирован в **собственном** реестре; ядро (`ModlistToolDeploymentProcessorRegistryV527`) пустое → `ROUTER.routeProject` без явного `registry` процессора не увидит. CP9 по умолчанию читает только CP8-реестр.
7. CP8 `outputPolicy.requiredPrefixes ['meshes/actors/']` (со слэшем) vs селектор `pathPrefixes ['meshes/actors']` (без) — разная граница сегмента; `normalizePath` в CP8 делает lowercase, в CP7 artifact пути не нормализуются → treeDigest зависит от регистра.
8. CP6 capture по умолчанию (самотест: maxLines 3) обрезает stdout до инспекции логов CP8; CP8 сам ставит 5000×65536, но fatal-строка после 5000-й потеряется → ложный pass.
