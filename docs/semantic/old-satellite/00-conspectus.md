# Старый Satellite «V2 Constructor Core» — конспект

Файл владельца `preview_40_file_windows_context_fix.html` (21 883 строки, `schemaVersion: 'satellite-0.6.4'`,
контейнер `.stll`). Прототип архитектуры, а не продукта: ядро ресурсов, окна, пробег. Структура по маркерам
`@sat:` — `structure.md`. Здесь — смысл по слоям, оценки и что берём (сводка — `BORROW.md`).

Пометки: **[берём]** — переносим в NG как принцип или контракт; **[меняем]** — идея верна, исполнение другое;
**[не берём]**; **[ошибка]** — дефект прототипа, который нельзя повторить.

## 1. Базис: constants, utils, identity, events (3 526–3 719)

- `constants`: имя приложения, версия схемы, расширение `.stll`.
- `utils`: `uid(prefix)` = случайные 8 символов base36; `key()` = trim + lower; FNV-подобный `hashText`.
  **[ошибка]** `hashText` — не FNV-1a (сдвиги вместо умножения на простое), коллизии непредсказуемы; для
  отпечатков в NG — настоящий FNV-1a / xxh3, как в `sat-scan::signature`.
- `identity`: `createId`, `displayKey` (имя → ключ), `sourceRef {source, lineNumber, rawLine, sourceKind, rawHash}` —
  **происхождение каждой сущности** (из какой строки какого файла пришла), алиасы «ключ → id[]».
  **[берём]** `sourceRef` как обязательное поле импортированной сущности: позволяет объяснить пользователю,
  откуда запись, и сверять при повторном импорте. **[берём]** правило «идентичность — id, не имя».
- `events`: шина `on/once/off/emit`, `*` — подписка на всё, история 400 событий, копия в `runtime.events`.
  Комментарий-принцип: «события не владеют истиной, только уведомляют». **[берём]** принцип. **[меняем]**
  строковые типы событий без схемы → типизированные события ядра (enum) + канал задач (NG-D003).

## 2. Реестр и контракты ресурсов (3 720–4 176)

- `registry`: плоские словари по видам ресурса — `primitives, wrappers, validators, importers, renderers,
  commands, commitActions, hotkeys, uiVariants, eventHandlers, jobs, extensions (манифесты), resourceContracts,
  runtimeApis, runContracts, barrierResolvers, presets`; `register*/get*`; пресеты раскрываются в списки ресурсов
  (`resolvePresetResources(presetIds, key)` с дедупликацией, порядок пресетов = приоритет).
- `resourceContracts`: нормализация каждого вида; **уровни доверия** `core → trusted-core`, `preset →
  trusted-preset`, `project → sandbox-required`, `external → explicit-approval-required`; возможности по
  примитиву (`primitive.window`: `selectionScope, projections, virtualized, virtualizerId, hotkeyScope,
  lifecycleScope`; `primitive.modRow`; `primitive.fileInput`); жизненный цикл `mount/update/unmount/invalidate` +
  `projectionScopes` (на какие проекции подписан ресурс); `requestedCapabilities`; `contractVersion: 1`;
  проверки обёртки (`missing-primitive`, `missing-renderer`) как issues, а не исключения.
  **[берём]** модель: вид ресурса + контракт + уровень доверия + запрошенные возможности + подписка на проекции.
  **[ошибка]** уровень доверия выводится из **префикса id** (`wrapper.core.*` → core): ресурс проекта с id
  `wrapper.core.x` получает доверие ядра. В NG доверие задаёт **источник загрузки** (бинарник / пакет пресета /
  контейнер проекта / внешний файл), id ни на что не влияет.
  **[ошибка]** `{...defaults, ...def, source, trustLevel}` — поля `def` перетирают нормализованные (кроме двух
  повторно присвоенных): ресурс может подсунуть свои `capabilities.virtualized` и т. п. В NG — строгая схема без
  неизвестных полей (как `CONTRACT_KEY_UNSUPPORTED` у монолита).

## 3. Политика и граница API (4 177–4 520)

- `resourcePolicy` — **активный** слой допуска (его вызывают runtime ресурсов, команды, хоткеи, UI-варианты,
  задачи): политика проекта `{allowTrustedCore, allowTrustedPreset, allowProjectResources=false,
  allowExternalResources=false, approved/blocked ResourceIds и ManifestIds, capabilityRules}`; правила
  возможностей: `window, render, command, hotkey, uiVariant, job, lifecycle, runtimeRead, runtimeWrite=false,
  commandDispatch, eventEmit, invalidation, jobStart, storageWrite=false, fileSystemWrite=false, network=false,
  worker=false`. Отказ → событие `resource.policy.blocked` с причиной (`blocked-resource`, `trust-policy`,
  `capability-policy`). **[берём]** deny-by-default для проектных и внешних ресурсов, явные одобрения, причина
  отказа как данные.
  **[ошибка]** правила возможностей — **глобальные на проект**, а не на ресурс: одобренный ресурс получает все
  включённые возможности, `requestedCapabilities` нигде не сверяются. В NG — грант возможностей **на ресурс** по
  его манифесту (что запросил и что пользователь подтвердил), проверка при каждом вызове.
- `runtimeApi.createForResource(resource, purpose)` — ресурс получает не глобальный `Satellite`, а замороженный
  объект: `read.{projectMeta, selection, window, mod, modRow, modlistProjection}` (глубокие копии),
  `commands.dispatch` (с `callerResourceId`, `callerTrustLevel`), `events.emit`, `invalidate.{ui,row,projection}`,
  `jobs.start`, `utils`. Запись — только через команды. **[берём]** главный принцип: **ресурс не трогает истину
  напрямую, только читает копии и шлёт команды**; каждый вызов проверяет возможность. **[меняем]** глубокое
  копирование через JSON на каждый вызов (дорого на больших сущностях) → в NG чтение через API ядра
  (сериализуемые ответы по запросу, срезы), в песочнице WASM граница и так копирующая.

## 4. Расширения и сборка контекста (4 521–4 804)

- `extensionLoader`: **манифест — единица расширения** `{id, title, version, source, trustLevel,
  enabledByDefault, dependencies[], resources{12 видов}, activeResources{startup/ui/command wrappers, hotkeys,
  validators, renderers, jobs, uiVariants, runtimeApis}, settings}`; регистрация ресурсов манифеста централизованно;
  `activeResources` — что включается, когда пресет/проект включает манифест. События `extension.registered`,
  `extension.project.bound`.
- `resourceComposer`: **стек пресетов** (`preset.core` всегда первый) → манифесты пресетов → активные ресурсы
  проекта (`startupWrapperIds, uiWrapperIds, commandWrapperIds, hotkeyIds, validatorIds, rendererIds, jobIds…`).
  Порядок стека = приоритет, дедупликация.
- **[берём]** манифест как единица расширения, разделение «зарегистрировано» и «активно в этом проекте», стек
  пресетов (`core + game pack + manager adapter` — PHILOSOPHY Фаза 3.5/4).
- **[ошибка]** `dependencies` объявлены, но нигде не проверяются (нет порядка загрузки и отказа при отсутствии).
- **[ошибка]** `{source: manifest.source, ...def}` — ресурс внутри манифеста может объявить себе `source: 'core'`
  и поднять доверие. И нет пространств имён: ресурс с чужим id молча перезаписывает зарегистрированный.
  В NG: id ресурса = `<манифест>/<локальный id>`, повторная регистрация — ошибка, источник наследуется от
  загрузчика и не переопределяется.

## 5. Runtime ресурсов: окна, подписки, жизненный цикл (5 530–5 788)

- Роды окон и обёртки по умолчанию: `modlist, meta, hotkeys, developerCenter, conflictChains,
  conflictToothTable, fileTree, fileManager, ignoredFiles, sameExtensionFiles` — **каталог родов окон NG**.
- `bindWindow(win)`: окно → обёртка (явная или по роду) → рендерер; проверка политики (заблокированное окно
  остаётся на холсте с пометкой `disabledByPolicy`, а не исчезает) → возможности и жизненный цикл в
  `win.resource`; вид по умолчанию из возможностей (`viewModes`, `defaultView`); `mount` один раз.
- `renderWindowBody`: рендерер получает `{targetEl, win, wrapper, api}` — API ресурса, а не глобальный объект.
- `handleInvalidation(dirty)`: окно перерисовывается, только если грязная проекция входит в его
  `capabilities.projections` (или `modlist:<win>` / `window:<win>`) — **подписка окна на проекции**.
- **[берём]** окно = экземпляр рода из реестра; подписка на проекции вместо «перерисовать всё»; блокировка
  политикой видима пользователю. **[меняем]** любое изменение выделения грязнит **все** окна (`uiDirty` при
  `selection`), а рендерер перерисовывает тело окна целиком (`innerHTML`) — в NG: каналы данных ADR 0009
  (окно подписано на конкретный канал выделения) и патчи строк ADR 0008.

## 6. Клавиши, команды, задачи (6 032–6 552)

- `hotkeys`: клавиша — **ресурс** `{combo, scope, priority, when(ctx), commandId | run}`; контекст нажатия
  `{modalOpen, activeWindow, selection, isInput, scope = modal | род активного окна | workspace}`; области
  `global`, род окна, `window:<id>`; в полях ввода работает только Escape; сортировка по приоритету.
- `commandRuntime.dispatch(id, payload)`: политика → `enabled` → `canRun` → `execute` либо запуск задачи
  (`command.jobId`) → журнал (200) → **объявленная инвалидация** (`invalidate: ['row:<id>', 'projection:<scope>',
  'indexes', 'allRows', 'ui', 'storage']`) → планировщик. События `command.dispatch.requested/blocked`,
  `command.execute.start/done/error`.
- `jobs`: задача — пакет выполнения (не истина): очередь, `concurrency` по очереди, `AbortController`,
  статусы `queued → running → done | failed | cancelled`, прогресс, события `job.*`; доступ к проекту в контексте
  задачи — только у доверенных.
- **[берём]** цепочку «клавиша (данные) → команда (ресурс) → проверка → выполнение / задача → объявленная
  инвалидация». Раскладка курсора ADR 0008 должна стать **клавишами-ресурсами по умолчанию**, переопределяемыми
  пользователем и расширениями. **[берём]** команда объявляет, что она грязнит (в NG — что она меняет в истине;
  проекции, зависящие от этого, инвалидирует граф зависимостей, а не автор команды).
- **[ошибка]** `concurrencyKey` нормализуется, но очередь использует только `concurrency.default` — ключ
  ничего не ограничивает. **[ошибка]** у задач нет поколений: результат отменённой/устаревшей задачи может
  примениться (в NG — `run::Authority`, ADR NG-D002 1c).

## 7. Модель проекта, хранение и жизненный цикл (15 006–16 641)

- **Схема проекта** (`.stll`, JSON): `meta` (id, имя, даты, исходные файлы), `profile` (стек пресетов, режим
  старта), `sourceFiles`, `resources` (активные ресурсы по видам, библиотека проектных ресурсов с одобрениями,
  доверие), `snapshot`, **`entities`** (`modsById`, `separatorsById` — по стабильным id), **`order`**
  (`separatorIds`, `globalModIds`, `modIdsBySeparatorId`, `pluginLoadOrder`), `indexes` (имя → id; помечены как
  наследие: «логика работает по id»), `rows` (производные строки), **`contextDescriptors`** — грани мода:
  `files`, `plugins`, `overwrite`, `scripts`, `future` с флагами `rowBadge` (значок на строке), `metaPanel`
  (секция меты), `heavyStorage` (данные в тяжёлом хранилище), `storageManifest` (тяжёлое хранилище: IndexedDB /
  OPFS / чанки), **`sync`** (`status`, `baseSnapshotId`, `debts[]`, `desiredState`), `ui` (окна, группы, холст,
  выделение, раскладка).
- `store`: один проект + runtime; `lifecycle`: **хранение и runtime разделены** — `toStorageProject` выкидывает
  `runtime` и производные `rows`, ставит флаги манифеста; `fromStorageProject` → миграции → нормализация;
  runtime-состояние (`projections.modlistByWindowId`, `metaByModId`, прокрутка, перетаскивание, виртуализация:
  порог 260 строк, overscan 10, высота строки 22 / разделителя 34, события, задачи, кеши) пересоздаётся.
- `projectFlow`: пути `new / import / load / save` — все сходятся в `activateRuntimeProject`: сверка ресурсов →
  регистрация проектных ресурсов → сброс runtime → привязка окон → пересборка строк и проекций → **проверка
  архитектуры** → событие → рендер.
- `architecture` (карта слоёв, потоков, правил) и `architectureGuard`: при старте, загрузке и регистрации
  проверяет **ссылочную целостность графа ресурсов** — у обёртки есть рендерер/команда/задача, у клавиши —
  команда, у окна — обёртка и рендерер, заявленная виртуализация имеет виртуализатор, активные ресурсы не
  заблокированы политикой; issues и warnings как данные.
- `migrations` (464 строки) — версии `.stll`; `normalize` — дозаполнение формы проекта.
- **[берём]**:
  - разделение хранения и runtime; производное не хранится (то же, что ADR 0002);
  - **грани мода (`contextDescriptors`)** — обобщённое «что о моде знаем»: каждая грань объявляет, даёт ли
    значок на строке и секцию в мете и где лежат её тяжёлые данные. Это ровно механизм твоих счётчиков и
    секций меты как данных; в NG — реестр граней, поставщики — анализаторы;
  - SYNC как «долги» между базовым снимком и желаемым состоянием (`debts`, `desiredState`) — та же модель, что
    записи SYNC ADR 0006, но в терминах «желаемое vs фактическое»;
  - единственный путь активации проекта, через который проходят все входы;
  - проверку ссылочной целостности графа ресурсов — в NG при сборке реестра (ошибка до запуска окна).
- **[меняем]** порядок как `separatorIds + modIdsBySeparatorId` (моды принадлежат разделителю, как в монолите)
  → плоский канон NG (`OrderBook`), блоки — запрос. Плоский порядок точно совпадает с семантикой MO2 и не
  требует синхронизации двух представлений.

## 8. Сущности, строки, инвалидация, проекции (16 643–17 693)

- `entities.createSeparator / createMod`: id из `identity.createId`, имя — только отображение (одинаковые имена —
  разные сущности), `identity {displayName, displayKey, sourceRef}`, флаги мода **`unmanaged, locked, movable,
  pseudo, officialDlc`**, `order {global, inSeparator, separatorId}`, **`contexts`** (грани с версией:
  `files {routeCount, uniqueRouteCount, hasDeepScan}`, `plugins {pluginCount, masterCount, dependentCount}`,
  `overwrite {conflictCount, win, lose, mixed}`, `scripts {scriptRouteCount, overwrittenScriptCount}`, `future`).
- `rows.rebuildOne` — **пакет строки** для UI: флаги, заголовок, `counters` (позиции, плагины, мастера,
  маршруты, конфликты, win/lose/mixed, скрипты), `badges`, `techTags`, `stickers`, `conflictStrip {severity…}`.
  **[берём]** идею «пакет строки = компактная выжимка граней мода для карточки»; в NG это `Row` ядра плюс
  счётчики граней, которые UI берёт для видимого окна, а не хранит на всех.
- `invalidator` — грязные корзины `rows / indexes / ui / storage / projections / allRows`; `scheduler` — **один
  flush на кадр** (`requestAnimationFrame`): инвалидация окон → проекции → рендер. **[берём]** «один пересчёт
  на кадр, а не на каждое изменение» и корзины по видам производного.
- `projections.buildModlistWindow(win)` — проекция **на окно**: секции по разделителям (свёрнутый = без строк),
  плоский список элементов с высотами (разделитель 34, мод 22) для виртуализатора, колонки (`splitRowsIntoColumns`,
  колонки — 2–8 по ширине окна / 170 px). Мета-пакет мода по выделению.
- **[ошибка]** `order.global` и `inSeparator` хранятся в каждой сущности — любое перемещение требует
  переписать позиции у всех модов между точками (O(n)), иначе позиции устаревают. В NG позиция — запрос к
  последовательности, не поле.
- **[ошибка]** проекция окна пересобирается **целиком** при любом изменении строк или порядка (O(n) на окно на
  событие) — ровно то, что лечит ADR 0008 (патчи строк). При этом идея «проекция на окно» верна — это вид ADR 0009.

## 9. Мутации и команды (17 694–18 066)

- `mutations` — маленькие изменения состояния: выделение (общее / окна), вкл/выкл, свёртка, вид окна,
  `moveModsBefore(ids, target, before|after)` (с `locked`/`movable`), и **каждое изменение канона дописывает
  «долг» SYNC** (`appendDebt`: `project.sync.status = 'dirty'`, `debts[]`). Команды — тонкий слой над мутациями.
- **[берём]** «любое изменение канона = долг перед MO2», который потом фиксируется планом; в NG это записи
  истории `OrderBook` + `manager_diff` (видимое расхождение канона с `modlist.txt`) → план фиксации NG-D003.
- **[ошибка]** `moveModsBefore`: фильтр `!moving.includes(id)` по каждому разделителю — O(n·k); затем полная
  пересборка `globalModIds` и позиций всех модов — O(n) на перемещение. На 7 500 модах терпимо, на 1 млн — нет.

## 10. Движок пробегов v3 (7 141–12 071, ~4 900 строк)

Комментарий-определение: **«Bucket = рекурсивная контрактная программа, runOrchestrator = маршрутизатор
контрактов, stage definition = переиспользуемая операция, stage run = параметризованный вызов, routeSource =
единица входа. Ветки порождаются фактами и контрактами стадий и сливаются обратно в родительский контекст».**

- **Каталог стадий** (`stageCatalog`): у стадии `kind, phase, requires[], provides[]` — **ключи фактов**
  (`facts.folderHandles.mods`, `facts.modSignatures`, `queue.routeSources`, `routes.indexed`,
  `barrier.routes.complete`, `plugins.registry`…). План строится из графа «требует → предоставляет», а не из
  жёсткого списка. Стадии: оркестратор (планировщик; фазы `inputDetection → surfaceSync → routeDiscovery →
  routeExpansion → routesComplete → commit`), surface (корень MO2, mods, overwrite, profiles — только мелкие
  метаданные, сигнатуры, долги SYNC), поиск источников маршрутов (каждый вход → work unit), глубокий анализ
  маршрутов (поток в routeSink: нормализация, хеш, пул, чанки, без усечения), доступ к архивам, парсер
  заголовков плагинов, **барьер `routes.complete`** («ни один анализ конфликтов / плагинов / скриптов / OAR не
  стартует до его закрытия»), сводка в проект.
- **Правило оркестратора:** «стадии возвращают факты и управление; вызвать другую стадию может только
  оркестратор».
- **Барьеры доступа:** стадия просит `ctx.access.request(access.readBinary)`; резолвер барьера (`archiveAccess`)
  открывает «закрытое содержимое архива» чтением одной записи по смещению, без распаковки архива целиком.
- **Правда о плагинах:** «`loadorder.txt` — истина порядка, `plugins.txt` — истина вкл/выкл, глубокий индекс
  маршрутов — истина физического существования и владения». Парсер читает только TES4: флаги, мастера, автор,
  описание, HEDR.
- **Хранение:** «`.stll` хранит источники, сигнатуры, счётчики, сводки архивов и ссылки на внешний индекс; не
  хранит миллионы сырых маршрутов». Маршруты — в сжатом дереве путей (`createCompactTreeStore`: имена → id,
  листья, восстановление пути по id листа) и чанках (5 000) в IndexedDB.
- Параметры пробега: `skipUnchangedMods`, `archiveManifestMode: manifest-only`, лимиты чтения архивов (128 МиБ)
  и заголовков плагинов (2 МиБ), `yieldEvery: 700`.
- **[берём]**:
  - **стадии с `requires/provides` по ключам фактов и план из графа** — это обобщение контракта анализаторов
    NG (сейчас порядок регистрации) до уровня стадий пробега, и это же даст правильный порядок для расширений;
  - правило «стадию вызывает только оркестратор»;
  - барьеры доступа с резолверами (ленивое чтение содержимого архива по требованию);
  - «в проекте — сводки и ссылки, сырые маршруты — в отдельном индексе» (совпадает с ADR 0007 и холодным
    ярусом NG).
- **[меняем]** три источника правды о плагинах (`loadorder.txt`, `plugins.txt`, индекс) — в NG это **стороны**,
  а канон порядка и включения плагинов — в проекте, расхождение со сторонами видно (как `manager_diff` для
  модов). Это и есть вероятная «ловушка версионности»: три файла с разными версиями правды без одного канона.
- Сжатое дерево путей ≈ `sat-core::interner::PathInterner` NG (арена строк + каталоги) — идея та же.

## 11. Пользовательские ресурсы проекта, Developer Center, ИИ (12 072–13 123)

- `projectResources`: библиотека ресурсов **внутри проекта** (`project.resources.projectLibrary`: ресурсы,
  одобрения, черновики фабрики, флаги `aiHandoffAware`, `extensionFactoryAware`). Ресурс-окно: режим `template`
  (HTML с подстановками `{{project.meta.projectName}}`), `javascript` (код рендера; нужно одобрение) или
  **UI DSL** (`ui.stack / card / heading / text / badge / button / list / table…` — декларативные узлы).
  Обёртка и рендерер генерируются из id ресурса (`wrapper.project.window.<slug>`).
- **Передача ИИ** (`buildAiContext`): пакет для модели — запрос («верни тело функции `defineExtension({...})`»),
  проект и активное окно, поддерживаемый API фабрики, списки доступных примитивов / обёрток / рендереров /
  команд / клавиш / задач, существующие ресурсы, примеры. Пользователь отдаёт пакет ИИ, вставляет ответ, фабрика
  (`runExtensionFactory`) превращает его в ресурсы. `developerCenter` — форма, предпросмотр, проверка, «Copy AI
  context», инъекция.
- **[берём]** — это самая сильная идея прототипа для философии NG («Эволюция»): **пакет контекста для ИИ +
  фабрика расширений + предпросмотр + одобрение**, и UI DSL как безопасный путь (данные вместо кода).
- **[ошибка, серьёзная]** одобрение хранится **в самом ресурсе** (`approvalStatus: 'approved'`, `spec.approved`
  от фабрики) и **в файле проекта**: чужой `.stll` с пометкой «одобрено» запустит свой JS при открытии.
  В NG одобрение — запись на машине пользователя (по хешу кода и манифеста), а не поле ресурса; открытие чужого
  проекта не исполняет его код без подтверждения (ADR 0007 п.7).
- **[ошибка, серьёзная]** код фабрики и JS-ресурсов исполняется через `new Function` в главном потоке: «API
  ресурса» — только соглашение, код видит глобальный `Satellite`, `window`, DOM. Фабрика исполняется **до**
  одобрения. Шаблоны пишутся в `innerHTML`. В NG: расширения — WASM в песочнице с API по возможностям;
  UI-расширения — только UI DSL (данные), без исполнения кода в UI.

## 13. Движок пробегов построчно (дочитано 2026-11-01)

Дочитано: тело `runEngine` 7 400–12 071. Источник тот же (одинаковы оба вложения, `cmp`).

### 13.1 Каталоги и барьеры (7 400–7 960)

- **Четыре каталога как данные.** Обёртки стадий (`stageWrapperCatalog`), валидаторы входа, решатели барьеров
  (`barrierResolverCatalog`) и контракты (`contractCatalog`). Контракт состоит из `{when, effect}`:
  - `when` — факт (`folder.detected` / `file.detected` / `sync.debt`), имя, родительский контекст и расширение;
  - `effect` — тип (`BRANCH_BUCKET`, `RESOLVE_BARRIER`, `RUN_STAGE_AFTER_BARRIER`, `REQUEST_ACCESS`,
    `SCORE_INPUT_MATCH`, `VALIDATE_INPUT_STRUCTURE`, `ALLOW_WITH_CONFIRMATION`) с параметрами.

  **[берём]** словарь эффектов как замкнутый перечень. Это та же модель, что `op` команд-ресурсов в NG (ADR 0011).
- **Барьер доступа.**
  - Запрос `{requestType, barrier, sourceKind}` выбирает решатель по словарю. Оценка совпадения —
    специфичность × 1000 + приоритет.
  - Барьеры: `archive.closed`, `archive.manifest.closed`, `archive.content.closed`.
  - Режимы решателя: `scoped-entry` — открыть архив, отдать поток или буфер записи, закрыть; `scoped-manifest`;
    `manifest-or-index`.
  - Продолжение записано в инструкции: `continuation: enqueueResolvedSource → deepRouteAnalysis`.

  **[берём]** доступ к содержимому закрытого источника идёт только через запрос. Решатель открывает источник на
  время запроса и закрывает его. Стадия не держит архивы открытыми.

  **[ошибка]**
  - нормализация `sourceKind` подстрокой (`includes('ba2')`);
  - запасной решатель жёстко зашит id (`|| 'resolver.skyrimMo2.archiveAccess'`);
  - `executeStage` разбирает стадии по цепочке `if (stage.id === …)`, так что каталог стадий не управляет вызовом.

### 13.2 Хранилище маршрутов (8 070–8 300, 8 937–9 210)

- **Компактное дерево путей.**
  - Узел — `[parent, nameId, isFile]`; имена интернированы.
  - Лист — id файла; у мода набор id листьев, упакованный дельтами (`encodeTreeLeafIds`).
  - Путь восстанавливается подъёмом от листа к корню.

  **[берём]** для холодного яруса: дельта-кодирование отсортированных id листьев мода. В NG сейчас есть
  интернированные пути (`interner`, `table`), а упаковки наборов для хранения нет.
- **Сток маршрутов** (`createRouteSink`) — единственный путь записи маршрута. Из одного прохода он получает:
  - лист дерева;
  - владение листом (`ownershipByLeafNodeId`, мод → конфликтные листья);
  - кандидатов в плагины, и россыпью, и в архивах;
  - обнаружение архива. Архив сразу превращается в инструкцию барьера, то есть в будущий «виртуальный
    источник маршрутов».

  Кроме того, сток считает счётчики по модам и расширениям и пишет чанки в IndexedDB (по 5 000 строк).

  **[берём]** «один проход — много фактов» (это и есть `StreamConsumer` в NG). Архив — источник маршрутов того же
  мода: его внутренние пути попадают в то же дерево и конфликтуют с россыпью.
- **Защита памяти.**
  - Полные строки путей не интернируются: их уже представляет дерево. В коде прямой комментарий о том, что
    иначе всё множество маршрутов дублируется в куче.
  - После `routes.complete` дерево и карта владения сбрасываются (`releaseDeepHeapBeforePostRouting`). Остаётся
    только то, что нужно стадии плагинов: кандидаты и записи архивов.

  **[берём]** у каждой фазы объявленный рабочий набор, остальное освобождается. Для NG это правило бюджета
  памяти фаз пробега.
- **Сессия хранит ссылки.**
  - Проект получает сводку пробега и ссылки вида `sessionId:compactTree`, `:ownership:*`,
    `:overwriteConflicts`, `:plugins`.
  - Манифест сессии (`routeManifests`) перечисляет все ссылки и счётчики.
  - В проекте держится до 30 последних сессий.
  - Сводки в сущностях мода урезаны: 250 конфликтных листьев, 80 цепочек, 24 архива.

  **[берём]** горячее хранит сводки с потолками, холодное — по ссылке. Это совпадает с ADR 0002 / 0007.

### 13.3 Конфликты перезаписи: файлы → цепочки → контексты (8 300–8 930)

Это главная недостающая часть NG-D002 (нормализованный слой цепочек).

- **Конфликтный файл.**
  - Лист с двумя и более владельцами, если путь не попадает в список игнора
    (`meta.ini, desktop.ini, thumbs.db` — настройка проекта).
  - Владельцы отсортированы по порядку. Победитель — последний; проигравшие — остальные.
- **Цепочка** (звезда вокруг якоря).
  - Для каждого мода-якоря берутся все его конфликтные файлы и все их совладельцы.
  - Якоря идут по убыванию числа конфликтных файлов. Повтор по сигнатуре отбрасывается.
  - Поля цепочки: участники с числом побед, файлы, 12 примеров путей, частое расширение и частое имя файла.
  - Заголовок: до трёх модов — `A → B → C`; иначе — `EXT · имя · первый мод`.
- **Контекст** — связная компонента цепочек через общие моды (обход в ширину).
- **Устойчивые id по сигнатуре.**
  - Сигнатура — хеш канонического JSON (`stableJson`): состав модов, листья, рёбра.
  - id сущности = хеш (префикс, сигнатура, порядковый номер).
- **Сверка с прошлым пробегом** (`reconcileOverwriteConflictEntities`).
  - Новые цепочки и контексты сопоставляются со старыми по сигнатуре.
  - Совпавшие сохраняют id и пользовательские решения (`completed`, `collapsed`, `userNote`) и получают статус
    `matched`. Несовпавшие — `new`. Исчезнувшие уходят в `removedChains` / `removedContexts`.
  - Контекст теряет «завершён», если изменилась хоть одна его цепочка.

  **[берём]** решение пользователя по конфликту — это вид истины «решения». Оно живёт на устойчивом id
  сущности, а id выводится из содержания. Сверка — та же модель, что SYNC: matched / new / removed.
- **Порядок меняет только победителей** (`patchOverwriteConflictsAfterOrderChange`). Состав цепочек и
  контекстов от порядка не зависит. После перемещения пересчитываются победители файлов, где участвует
  перемещённый мод, затем `winnerCounts` их цепочек и статистика затронутых модов (выигрыши, проигрыши,
  «смешанный»).

  **[берём]** для NG это прямой план инкрементальной перезаписи. Перезапись делится на две проекции:
  - структура конфликтов ← факты;
  - победители и статистика ← структура + приоритеты.

  Вторая инвалидируется по ключам канона: перемещённые моды → их конфликтные файлы. Это следующий шаг после
  сессии (`@sat:session`).
- **[ошибка]**
  - сигнатура цепочки строится по владельцам, **отсортированным по порядку**, поэтому перестановка модов меняет
    сигнатуру. Повторный пробег после перемещения теряет решения пользователя. В NG сигнатура — от множества,
    упорядоченного по id;
  - патч после перемещения обходит **все** конфликтные файлы, а не индекс мод → файлы;
  - `find` по массивам внутри циклов (`getAffectedOverwriteModIds`) даёт O(n²);
  - заголовок цепочки хранится, хотя это проекция (вычисляется из имён).

### 13.4 Вход, оркестрация, фазы (9 214–10 340)

- **Проверка входа с оценкой.**
  - Ищутся подпапки `mods/profiles/overwrite`. Если их нет, папка распознаётся как частичный корень: только
    `mods` (по совпадению имён папок с проектом ≥ 40 % или по имени `mods`), только `profiles` или только
    `overwrite`.
  - Оценка = 35 % структура + 45 % совпадение имён модов + 20 % файлы профиля и совпадение `modlist.txt`.
  - Зелёный — ≥ 90, жёлтый — ≥ 60 и только с явным подтверждением, иначе красный.
  - Совпадение имён = среднее двух долей пересечения, то есть симметрично.

  **[берём]** для `sat-cli analyze` и будущего мастера: входу выставляется оценка, частичный корень допустим с
  подтверждением, и пользователь видит причину.
- **Быстрая подпись поверхности** (`v1-fast`): имя папки + число записей + отсортированные имена папок, файлов и
  расширений корня. В NG это закрыто подписями v2 / v3 (`sat-scan`).
- **Оркестратор.**
  - Журнал фактов (`emitFact`, индекс по типу).
  - Ветки по контрактам корня: mods / overwrite / profiles.
  - Фаза расширения маршрутов — цикл до неподвижной точки: глубокий проход по ожидающим источникам → решатели
    архивов → архивы ставятся в очередь как виртуальные источники → следующий проход.
  - Защита от зацикливания — 24 прохода.
  - Прямой комментарий: ветки архивов не запускают рекурсию, а только ставят источники в очередь.
  - Барьер `routes.complete` закрывается проверкой «нет ожидающих источников»
    (`assertRoutesComplete` бросает ошибку). Только после него идут стадии `post-routing` (плагины).
  - Overwrite — отдельный источник маршрутов `mo2:overwrite` с наивысшим приоритетом.

  **[берём]** расширение источников как очередь до неподвижной точки с лимитом. Пост-стадии только за барьером.
  У NG `SourceExpander` и `routes.complete` уже в контракте анализаторов; в NG-D002 нужно явно добавить лимит
  проходов и проверку барьера.

### 13.5 Архивы (10 340–11 050)

- BSA: заголовок 36 байт, папки по 16 байт (Skyrim). Бит сжатия `0x40000000` инвертирует флаг архива `0x0004`.
  Глобальная таблица имён — после блоков папок.
- BA2: магия `BTDX`, таблица имён по смещению. Сжатость определяется по `unpacked > packed`.
- Чтение содержимого: срез файла, затем zlib через `DecompressionStream`, если он есть. Иначе запись помечается
  `needsDecompression` с причиной, а не тихой ошибкой.
- **[ошибка]**
  - два полных парсера каждого формата: из `File` срезами и из `ArrayBuffer`;
  - у сжатой записи BSA размер перед zlib-потоком угадывается («common BSA … store unpacked size»).

  В NG парсер один (`sat-formats`), а источник байтов — абстракция.

### 13.6 Плагины (11 050–11 460)

- **Три источника объединяются**: `loadorder.txt`, `plugins.txt` (`*` — включён) и обнаруженные в маршрутах
  кандидаты (россыпь и архивы, по всем модам).
- **Состояния плагина**: `ordered`, `listedInPlugins`, `discovered`, `enabled`.
  - Обнаружен, но не в списках — `discoveredOnly`, помечается как «скрыт лимитом MO2».
  - В списке, но не обнаружен — `missingOnDisk`.
- **Заголовок TES4.** Флаги ESM `0x1` и ESL `0x200`. `HEDR`: версия (float), число записей, следующий id
  объекта. Плюс `MAST`, `CNAM`, `SNAM`. Чтение ограничено 2 МБ, через `requestAccess` (то есть и из архива).
- **Тип.** `esm` / `esm-light` / `esl` / `espfe` — по расширению и флагу.
- **Индексы.** Активные плагины в порядке загрузки получают полный индекс (`00…FD`) или лёгкий
  (`FE:000…FFF`).
- **Граф мастеров**: `mastersByPluginId`, `dependentsByMasterName`.
- **[ошибка] — подтверждает «ловушку версионности» владельца:**
  - версия `HEDR` читается, но **нигде не проверяется**: нет допустимых версий по игре, не проверяется, можно
    ли ESL-флаг при этой версии, нет предупреждения о версии 0.94 / 1.70 / 1.71;
  - плагин «обнаружен вне списков» объявляется скрытым лимитом MO2, хотя чаще это просто выключенный мод.
    Состояние нужно выводить из `mod enabled × plugin checked`, как решено для NG;
  - `primary` — первый найденный кандидат, а не победитель по приоритету мода. Если плагин с одним именем лежит в
    двух модах, читается не тот файл;
  - нет проверки отсутствующих мастеров и порядка мастер → зависимый, хотя граф уже построен;
  - лимит полных индексов (254 / 255) не проверяется;
  - `dependentCount` по моду считается `Object.values().filter` внутри цикла по модам, то есть O(n²).

### 13.7 Итог пробега (11 460–11 610)

- `applyDeepSummaryToProject` / `applyPluginSummaryToProject` пишут сводки в сущности модов и `project.indexes`,
  затем помечают строки и проекции (`invalidator.markRow / markProjection / markStorage`).
- `finalizeSession` — компактный итог: фазы, проходы, состояние барьеров, счётчики.

  **[берём]** итог пробега как данные с журналом фаз (у NG — `run` + отчёт `sat-cli`).

  **[ошибка]** итог применяется к проекту по частям во время пробега, а не публикуется целиком. В NG — поколение
  + печати (`run::Authority`).

## 14. Остальные области (дочитано 2026-11-01)

- **`migrations` (16 042–16 505).**
  - Реестр шагов `from → to`, упорядоченный список версий.
  - Отказ открывать проект новее сборки; защита от цикла.
  - Сохраняется `originalSchemaVersion`, ведётся журнал применённых шагов.
  - Старые файлы без метаданных считаются первой версией с идентичностью и нормализуются.

  **[берём]** для формата проекта и контейнера (ADR 0007): цепочка шагов, отказ «новее меня», журнал.
- **`importers` (16 909–17 125).**
  - `modlist.txt` читается снизу вверх (у MO2 верх = высший приоритет).
  - Номер строки источника сохраняется у каждой записи (происхождение).
  - Разделитель хранится как запись-«представитель», чтобы доказать, что он был в файле.
  - Моды до первого разделителя попадают в системный разделитель.
  - `*` считается включённым (у MO2 это неуправляемый мод).

  **[берём]** номер строки как происхождение. **[ошибка]** `*` ≠ «включён»: это отдельное состояние (у NG —
  Foreign).
- **`selectors` (17 126–17 245)** — тонкие чтения проекта (`modIdsForSeparator`, `separatorIds`, высоты). Новых идей
  нет.
- **`resourceCenter` (4 814–5 529).**
  - Индекс ресурсов с диагностикой связей: обёртка без примитива; окно без рендерера; команда или клавиша на
    незарегистрированную команду — ошибка.
  - Обратные ссылки: где используется рендерер или команда.
  - Активация и деактивация ресурса.

  **[берём]** диагностика связей как данные — в NG это `Decision::Blocked` с перечнем отсутствующих (ADR 0011).

  **[ошибка]**
  - `reconcileProjectResources` только добавляет id (`mergeUnique`) и никогда не удаляет, так что списки активных
    растут;
  - «можно ли показать окно» реализовано дважды: `resourceCenter.canExposeWindowNode` и
    `windowLibrary.isContextAllowed`;
  - контекст окна сверяется подстрокой (`includes('mods')`).
- **`windowLibrary` (6 791–7 149).** Список родов окон с предпросмотром и параметрами обёртки. Новое окно
  ставится каскадом от точки вставки (+28 px). Для списка модов параметр `isolateModSelection` выбирает режим
  `isolated` или `shared`.

  **[ошибка]** вставка окна **сама активирует** ресурс-обёртку в проекте («Window Library is the application
  front»). Это активация без одобрения. В NG вставка окна неодобренного рода ведёт в запрос одобрения.
- **`startWizard` (18 133–18 639).**
  - Режимы: продолжить / загрузить / новый.
  - Шаги нового проекта: имя → пресеты → источники, с проверкой каждого шага.
  - Имя файла: `<Имя>.<Пресеты>.stll`, очищенное от запрещённых символов.
  - Можно подгрузить файл обёртки с проверкой.
- **`scrollState` (18 639–18 755).** Позиции прокрутки сохраняются по устойчивому ключу (`data-scroll-key`, окно +
  роль, модалка + роль) вокруг каждого полного перерендера. Это **[симптом]** полного перерендера: в NG окна
  обновляются патчами, и такого хранителя нет.
- **`diagnostics` (19 385–19 816).** Инспектор ресурсов, окон и модов: снимок без функций (`stripFunctions`). В NG
  то же даёт отчёт `sat-cli` + семантическая карта.
- **CSS (1–3 515).**
  - 18 токенов на `:root`: тёмная палитра `bg / panel / panel2 / line / text / muted / accent / ok / warn /
    danger`; фиксированные размеры `toolbar 44`, `window-head 34`, `row 26`, радиус 5; два шрифта.
  - `contain: content` у окон.
  - Шесть точек перестроения под узкие экраны (850–980 px).
  - Сплиттеры dock по двум осям.

  **[берём]** фиксированную высоту строки как контракт виртуального списка (у NG так и есть).
