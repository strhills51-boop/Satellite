# ADR 0007 — Проект `.stll`: самостоятельный проект сборки

- Статус: **принято (направление)** (2026-11-01, владелец); формат разделов уточняется по мере реализации
- Связано: ADR 0002 (ярусы), 0006 (канон в проекте, записи SYNC), 0011 (ресурсы), 0013 (правила как данные);
  PHILOSOPHY §3 «Указатели», «Техпроцесс», «Модель сервиса»
- Заменяет прежнюю редакцию (контейнер по образцу `.mnlth` монолита и импорт `.mnlth`): **без обратной
  совместимости с монолитом** — решение владельца 2026-11-01 («монолит мертворожденный»).

## Суть (владелец)

`.stll` — это **проект**, и он **самостоятелен**: пользователь работает с ним вне сборки. Пример владельца: на
сайте Satellite он увидел новые моды, не скачал их, но оставил в проекте запись SYNC — «поставить вот так». Дома,
за компьютером со сборкой, он нажимает «фиксация» в том же проекте — мод скачивается и ставится так, как он
настроил это заранее. На сайте проект должен разворачиваться быстро.

Отсюда три следствия, которые определяют всё остальное.

1. **Проект — желаемое состояние сборки, а машина — исполнитель.** Сверка с диском — лишь один источник записей
   SYNC. Записи-**намерения** создаются где угодно (сайт, другой компьютер, правило) и исполняются фиксацией там,
   где есть сборка. Техпроцесс «скан → обработка → фиксация» не меняется: меняется то, что обработка не требует
   диска.
2. **Проект несёт факты, а не только решения.** Чтобы вне сборки видеть конфликты, дерево файлов, плагины,
   метрики, в проекте лежат **пути модов** и их метрики (холодный ярус): у каждого мода — манифест файлов
   (путь, размер, VRAM, архивные записи) и заголовки плагинов. Без диска проект показывает то же, что с ним.
3. **Мод может существовать в проекте раньше, чем на диске.** Сущность «запланированный мод»: источник
   (указатель), версия, выбор установщика, место в порядке, включён ли. Если манифест его файлов известен
   (от сообщества или из прошлой установки), конфликты видны **до скачивания**.

## Решение

### Модель

- **Устойчивые id сущностей** (мод, разделитель, группа): имя — атрибут. Переименование — правка атрибута, а не
  новая сущность; менеджеры без папок-модов (Vortex) ложатся в ту же модель. Это первый шаг реализации: на id
  стоят все разделы.
- **Ядро и пакеты разделов.** Ядро знает общие разделы; пакеты игры и менеджера добавляют свои
  (`bethesda.plugins` — только игры Bethesda, `mo2.profile` — только MO2). Неизвестные разделы сохраняются как
  есть: проект, открытый без расширения или старой версией, не теряет чужие данные.
- **Привязка к машине — вне проекта.** Где лежат `mods`, профиль, кеш — маленький файл на машине. В проекте нет
  абсолютных путей и машинных идентификаторов.

### Файл

`.stll` — один файл-архив (zip: открывается любой программой, разделы читаются по одному, сохранение атомарно
через временный файл). Внутри:

| Раздел | Формат | Что | Публичный |
|---|---|---|---|
| `manifest.json` | JSON | формат, версия схемы каждого раздела, хеши, игра и менеджер, публичность разделов; пишется последним | да |
| `project/entities.ndjson` | NDJSON | сущности с id: вид, имя, источники (указатели), внешняя идентичность (Nexus id, хеши, версия) | да |
| `project/order.ndjson`, `decor.ndjson`, `marks.ndjson`, `decisions.ndjson`, `settings.ndjson` | NDJSON | порядок и вкл/выкл, декорации и стили, метки, решения по цепочкам, игнор-лист и наборы правил | да |
| `project/sync.ndjson` | NDJSON | записи SYNC: расхождения со сборкой **и намерения** (поставить, обновить, удалить, перенести) | частично |
| `journal.ndjson` | NDJSON | журнал команд (история и отмена между сессиями; позже — наблюдения для сообщества) | нет |
| `facts/<id>.bin` | бинарный, сжатый | манифест файлов мода, метрики, заголовки плагинов — по моду, с подписью содержимого | да |
| `extensions/` | дескрипторы, WASM | пользовательские модификации с манифестом прав | по выбору |

Почему так:

- Истина пользователя — небольшая и ценная, её сравнивают между версиями и ею делятся: NDJSON, одна запись — одна
  строка с id.
- Факты — большие и пересобираемые с диска: бинарно и **по моду**. Сайт грузит манифест и разделы проекта сразу,
  а факты — лениво, по видимым модам (zip даёт читать запись по смещению). Мод с той же подписью содержимого не
  перезаписывается: сохранение после скана пишет только изменившиеся моды.
- Факты — **часть проекта по умолчанию** (самостоятельность), но помечены «пересобираемые»: при нехватке места их
  можно выбросить и восстановить сканом.

### Фиксация с намерениями

План фиксации (`@sat:sync.plan`) получает операции получения: «скачать из источника → проверить хеш → установить
(с сохранённым выбором установщика) → поставить в порядок → включить». Источник — указатель (PHILOSOPHY
«Указатели»); скачивание — адаптер площадки с правами пользователя (ключ, вход) и его подтверждением. Всё прочее
в фиксации — как сейчас: бэкап, журнал, откат.

## Порядок работ

1. Устойчивые id сущностей в каноне и книге порядка; проект адресует всё по id.
2. Холодный ярус: факты мода в бинарном формате с подписью содержимого; запись и чтение по моду; открытие
   проекта без сборки (перезапись, плагины, метрики — из фактов проекта).
3. Файл `.stll`: манифест, разделы, атомарное сохранение, хеши, неизвестные разделы сохраняются; привязка к машине.
4. Записи-намерения и запланированные моды; операции получения в плане (сначала «из локального архива», затем
   адаптеры площадок).

## Сделано

- Шаг 1 (2026-11-01): `sat-core::entity` — id (`e` + 16 знаков base-32: время и счётчик), реестр id ↔ имя;
  проект — схема 2: `entities`, декорация (цвета, группы, стили, метки) и подписи содержимого — по id; файл
  схемы 1 мигрирует при чтении (`Project::from_json`); фиксация переименования (`apply_plan`) сохраняет сущность
  со всем, что на ней висит — проверено на копии сборки. Книга порядка внутри сессии по-прежнему работает с
  именами, перевод — на границе проекта (`Decor::rekey`). **Ещё не по id:** решения по цепочкам (подпись цепочки
  считается от имён модов — переименование мода переоткрывает его цепочки), записи SYNC (они по природе об
  именах папок).

- Шаг 2, первая часть (2026-11-01): крейт `sat-stll` — факты мода в проекте (`facts/<id>.facts`, bincode, формат 1,
  подпись содержимого; мод с той же подписью не перезаписывается; факты ушедших сущностей удаляются);
  `sat-cli analyze` пишет их после скана и читает вместо скана с `--offline`; `sat-devserver --project <папка>`
  открывает проект **без сборки** — порядок, декорации, конфликты, цепочки, плагины, метрики из проекта. Проверено:
  папка `mods` убрана — те же 229 конфликтных путей и 172 цепочки. **Ещё нет:** списков менеджера по плагинам в
  проекте (раздел `bethesda.plugins`) — вне сборки плагины считаются без `loadorder.txt`/`plugins.txt`; подписи
  содержимого отдельных файлов (для ADR 0014); сжатия (придёт с zip-контейнером).

## Последствия

- `sat-cli` и devserver переходят с `project.v0.json` на `.stll` после шага 3; до этого `project.v0.json` остаётся
  временной точкой сохранения.
- Монолит не импортируется: данные владельца переносятся заново через NG (скан, правила, ручная разметка).
