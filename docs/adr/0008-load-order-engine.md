# ADR 0008 — Движок порядка загрузки: канон, декорации и вид, изменяемые только патчами строк

- Статус: **принято** (2026-10-31)
- Связано: ADR 0002 (слои истины), ADR 0006 (канон в проекте), ADR 0007 (контейнер), PHILOSOPHY §5
- Код: `crates/sat-core/src/order/` (`seq.rs`, `book.rs`, модельные тесты `tests.rs`), бенчмарк `sat-cli bench-order`

## Контекст

Список модов — ядро монолита: порядок загрузки, разделители, вкл/выкл, цвета, логические группы, свёртка, фильтры.
В монолите он перерисовывался целиком (`renderAll` переназначен 11 раз, `renderClassic` 6 раз), а точечные пути
появлялись по одному под конкретные сценарии (`rerenderAfterMutation` с ветками по `__modlistMutationScope`,
оптимистичная посадка DOM на телефоне CP12/CP15, патч карточки в модалке конфликтов). Итог: каждое новое
действие — новая ветка «что перерисовать», и на ~1 000 модов интерфейс становился тяжёлым.

Лучшая находка поздних версий — **Logical Group NG** (v557–v590): группа модов показывается одной строкой
(композитный мод), а канон порядка не меняется; в `modlist.txt` группа живёт маркерами `⟦MLT-LG:v1:id:k/n⟧`.
Это и есть принцип «декорация поверх канона», только реализованный в монолите на отдельном слое со своими кэшами.

## Решение

**Один движок, три слоя, один протокол изменений.**

1. **Слои** (`OrderBook`):
   - *канон* — порядок и вкл/выкл (то, что уходит в `modlist.txt`);
   - *декорации* — цвет, логические группы. Хранятся рядом с каноном и **никогда не меняют порядок**;
   - *вид* — свёрнутые разделители и группы, фильтр. Решают только, какие записи становятся строками.
2. **Протокол**: любая операция возвращает `Change { revision, len, patches }`, где патч — `Remove`, `Insert`,
   `Update` (диапазоны строк) или `Reset` (только смена фильтра). Индексы патчей последовательны: каждый
   относится к строкам после предыдущего. Содержимое строк UI запрашивает сам (`rows(start, count)`) — только для
   своего видимого окна. **Полной перерисовки нет ни в одном сценарии**; UI держит число строк и окно.
   Номер позиции (приоритет MO2) патчами не покрывается: одно перемещение сдвигает номера всех записей между
   источником и целью. Поэтому после каждого изменения UI перечитывает своё окно (десятки строк) и пишет в DOM
   только строки, чьё содержимое изменилось.
3. **Структура**: последовательность ключей кусками по 256–512 с агрегатами на кусок (записи, видимые строки,
   разделители) и деревьями Фенвика над порядком кусков. Позиция ключа, ключ на позиции, ключ на строке, начало
   и конец блока разделителя — O(log кусков + размер куска). Удаление не двигает соседние куски; пустые и мелкие
   сворачиваются в конце операции.
4. **Семантика перемещения** совпадает с `canon::Modlist::move_entries` (тест сверяет на 800 случайных
   перемещениях): разделитель едет со своим блоком, относительный порядок сохраняется, цель внутри набора — no-op.
   Дополнительно (из монолита): строка свёрнутой группы едет со всеми членами; чужой мод, брошенный внутрь
   группы, встаёт перед ней (`resolveLogicalGroupAwareModDropAnchor`).
5. **Логическая группа** — непрерывный отрезок модов одного блока (правила монолита 44353: ≥2 мода, подряд, без
   членов другой группы). Нарушенная группа (в неё вставили чужой мод) показывает членов обычными строками и
   **не прячет их** — в монолите разделитель в этом случае рендерился пустым (S04 §4.2).
6. **История**: операции канона и декораций обратимы (перемещение ↔ «поставить на позиции», флаги ↔ прежние
   значения, группа ↔ роспуск). Состояние вида в историю не входит. Полный откат возвращает исходный канон —
   проверяется тестами и бенчмарком.
7. `canon::Modlist` остаётся снимком канона (сериализация, проект). Книга строится из него и выгружается в него.

## Доказательства

- Модельный тест: 150 зёрен × 1 500 случайных операций (перемещения, вкл/выкл, цвет, свёртка, группы, фильтры,
  undo/redo). После каждой: зеркало UI, обновлённое **только патчами**, совпадает с видом построчно (вместе
  с содержимым — так ловятся пропущенные `Update`), вид совпадает с пересчётом с нуля, инварианты кусков целы.
- `sat-cli bench-order`, 1 000 000 записей (разделитель на каждые 50), сборка release, контейнер:

| Операция | Время |
|---|---|
| Сборка книги | 339 мс, 259 МиБ |
| Чтение окна 60 строк | 0,033 мс |
| Перетащить одну запись куда угодно | 0,072 мс |
| Перенести 10 000 разбросанных модов | 50 мс |
| Перенести блок разделителя наверх | 0,28 мс |
| Переключить 100 000 модов | 110 мс |
| Свернуть разделитель | 0,087 мс |
| Фильтр по имени / сброс | 37 мс / 14 мс |
| Создать группу | 0,062 мс |
| Откатить 1 004 операции | 168 мс |

Демо: `Order Lab` — JS-зеркало ядра с виртуальным списком на 1 млн строк (артефакт; тот же модельный тест
прогнан и для зеркала). Перетаскивание, вкл/выкл, цвет, группы, свёртка, фильтр, отмена; счётчик записанных
DOM-строк показывает, что каждое действие трогает только окно.

## Сделано после принятия

- Вставка и удаление записей (`insert_entries`, `remove_entries`) тем же протоколом и с отменой; удалённая запись
  остаётся «надгробием» до конца истории. Удаление разделителя присоединяет его блок к блоку выше. Участника
  группы удалить нельзя, пока группа не распущена (правило мини-редактора монолита: минимум два члена).
- Декорации как данные (`order::decor::Decor`): цвета, группы, свёрнутые разделители по **именам**, в
  `Project.decor` (поле необязательное, старые файлы читаются). Сломанная группа сохраняется и загружается
  сломанной, а не отбрасывается. Загрузка декораций очищает историю.
- Кодек маркеров монолита: `name ⟦MLT-LG:v1:<id>:<k>/<n>⟧` (id в `encodeURIComponent`), разбор берёт последний
  маркер строки; импорт строгий: маркер на не-моде, неверный маркер, два маркера в строке, расхождение числа
  членов, недостающие или лишние, повтор порядкового номера, разрыв, порядок номеров ≠ физический — всё
  ошибки, ничего не чинится молча. Маркеры — только для экспорта и импорта; настоящий `modlist.txt` MO2 их не
  содержит.

- **Клавиатурный курсор** (`order::cursor`), как двухэтапное выделение монолита: фокус (одна запись, рамка из
  двух уголков), якорь и выделение — ключи записей, поэтому переживают перемещения, фильтры и свёртку. Изменения
  курсора — те же патчи (`Update`); больше 4 096 затронутых строк — одним `Update` на весь список. Раскладка:
  стрелки / PgUp / PgDn / Home / End; Shift — диапазон от якоря (через границы разделителей, в отличие от
  монолита); Ctrl — только фокус; Пробел — в выделение / из выделения; Alt+↑↓ — выделенное на строку, а
  разделитель — на блок целиком (иначе он врезался бы в соседний блок и забирал его хвост); Alt+Shift+↑↓ — к
  началу / концу блока; ← → — свернуть / развернуть, ← на моде — к его разделителю; буквы — поиск по началу имени.
  На миллионе записей: шаг фокуса 0,04 мс, Shift+PgDn на 100 000 строк 4 мс, Alt+↓ блока 0,12 мс.
- **Приглушение** (`set_muted`, `Decor.muted`): пользовательский флаг «не планирую, пусть не мешает». Запись
  остаётся в анализе и каноне, вид её скрывает, пока фильтр не попросит `show_muted`. Это декорация, а не
  отдельный список.

## Открыто

- Классический вид монолита — сетка карточек с переносом, а не список: раскладка строк сетки поверх тех же патчей
  (строка вида → карточка; переносы считает UI по ширинам).
- `Update` после массового переключения — десятки тысяч диапазонов; при необходимости сжимать до «диапазон +
  битовая маска» или до `Reset` выше порога.
- Сборка ядра в WebAssembly (в CI; в контейнере нет `rust-std` для wasm32).
- Переименование записи — `rename` (с отменой); связать с решением записи SYNC `fs_renamed` — в слое приложения (NG-D003).
