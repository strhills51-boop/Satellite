# NG-D003 — Слой приложения и dev-оболочка

- Статус: **open** (запланирована, после NG-D002)
- Пункты карты: PHILOSOPHY §8 Фаза 0 (граф зависимостей проекций, jobs), Фаза 3.5 (реестр команд)
- ADR: 0002, 0004, 0006

## Цель

Единый конвейер приложения поверх ядра: команды, запросы, события, поколения, задачи с отменой —
и тонкая dev-оболочка (HTTP + WebSocket), на которой UI и Playwright-тесты работают без Tauri.

## Контракт закрытия (черновик)

1. `sat-app`: типы Command / Query / Event с serde; экспорт TypeScript-типов автоматически.
2. Конвейер команды: `dispatch → policy → mutation слоя → invalidation → новое поколение → event`;
   команды не трогают UI (правило прототипа Satellite `no-render-from-command`).
3. Проекции объявляют зависимости; изменение порядка пересчитывает только перезапись, а не таблицу (проверено тестом).
4. Задачи (пробег анализа) отменяемы; устаревший результат не публикуется (поколение, как `superseded` в процессорах монолита).
5. **Решения по записям SYNC** (сами записи создаёт пробег, NG-D002): статусы `pending / confirmed / ignored /
   resolved` как команды; при `pending` фиксация заблокирована.
6. (перенесено в NG-D002: сверка и импорт проекта)
7. **Фиксация:** `Plan` операций → pre-commit проверка (отпечаток записей, свежесть пробега) → версия-бэкап
   (`modlist.txt`, проект до) → применение → журнал; удаление = перенос в `deleted/<время>`. Проверено на копии
   сборки во временной папке, включая откат при ошибке на середине.
8. `apps/devserver`: HTTP для команд и запросов, WebSocket для событий; сценарий «открыть → пробег → решить записи
   SYNC → переместить мод → undo → зафиксировать с бэкапом» проходит интеграционным тестом.
9. Бюджеты: ответ запроса видимой страницы < 50 мс на сборке 2,9 млн файлов.

## Вне рамок

UI один в один (NG-D003+), Tauri-оболочка (после того, как UI работает на dev-сервере).

## Решения

- **Фиксация (п. 7), 2026-11-01.** Три слоя, каждый со своим владельцем:
  - ответ на запись — `Resolution` (матрица монолита, `@sat:sync.records.resolution`): `adopt_to_project`,
    `move_to_deleted`, `create_disk_folder`, `remove_from_project`, `accept_fs_name`, `rename_disk_to_project`;
  - план — чистая функция `sync::plan::plan(canon, records, disk)` (`@sat:sync.plan`): изменения канона, операции на
    диске по зависимостям (освобождение имён → переименования → создание), все блокеры до первой операции:
    `pending`, нет ответа, ответ не подходит, **запись устарела** (диск уже не показывает это расхождение — это и
    есть проверка свежести перед фиксацией), нет источника, цель занята, две операции в одно имя, цикл
    переименований, разделитель с модами;
  - исполнение — `sat_mo2::commit::execute` (`@sat:mo2.commit`): `versions/<метка>/` с копиями `modlist.txt`,
    `plugins.txt`, `loadorder.txt`, `project.before.json` и `commit.intent.json` до любых изменений; операции по одной
    с журналом `commit.journal.json`; `modlist.txt` и проект — через временный файл; при ошибке на любом шаге —
    откат журнала в обратном порядке и восстановление файлов профиля; `commit.rollback.json` пишется всегда.
- **Где `deleted/`** (открытый вопрос 1 конспекта SYNC): `<экземпляр>/satellite/deleted/<метка>/` — рядом с `mods` в
  обычной раскладке, перенос — `rename` на одном томе. Если `mods` на другом томе, `rename` падает и фиксация
  откатывается: Satellite не копирует и не удаляет моды за спиной пользователя.
- **Принятая папка** (`adopt_to_project`) встаёт в конец списка (мод — включённым). У монолита — служебный разделитель
  «FS / Imported» перед SYNC; в NG разделитель — тоже папка, и созданный задним числом дал бы новую запись при
  следующем анализе.
- Командная строка: `sat-cli sync <экз.> [--decide N ОТВЕТ]` и `sat-cli commit <экз.> [--apply]`; без `--apply` —
  только план. Проверено на копии сборки: переименование, пропавший мод, пропавший разделитель, новая папка →
  решения → фиксация → повторный анализ без расхождений. Откат проверен тестом на каждом шаге.
