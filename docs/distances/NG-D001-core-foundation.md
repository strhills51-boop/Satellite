# NG-D001 — Фундамент ядра на Rust

- Статус: **closed** (2026-10-30)
- Пункты карты: PHILOSOPHY §8 Фаза 0 (перенос фундамента, тесты форматов, бенчмарки)
- ADR: 0001, 0002, 0003, 0005

## Цель

Перенести проверенную модель данных прототипа v0.1 (Go) в Rust-воркспейс с правильными границами слоёв,
так чтобы на ней можно было строить приложение (NG-D002) без переделок фундамента.

## Контракт закрытия

1. Воркспейс `crates/`:
   - `sat-core` — без `std::fs`/сети; интернер путей, `ProviderTable`, проекция перезаписи (стеки, exact chains,
     contexts, W/L/M/X/+n, VRAM победителей);
   - `sat-formats` — TES4-заголовок и счёт записей, BSA v103–105, BA2 GNRL/DX10, DDS → VRAM;
   - `sat-mo2` — ModOrganizer.ini, modlist/plugins/loadorder.txt (round-trip байт в байт), meta.ini, QColor;
   - `sat-scan` — параллельный обход (rayon), сигнатуры, кеш сканов.
2. `cargo test --workspace` зелёный; `cargo clippy --workspace -- -D warnings` чистый; `cargo fmt --check` чистый.
3. Зависимости только с permissive-лицензиями (ADR 0003): проверка списком `cargo metadata`.
4. **Сверка с эталоном:** на одной и той же синтетической сборке Rust и Go дают одинаковые
   число путей, провайдеров, конфликтных путей, цепочек, контекстов и W/L/M для каждого мода.
5. **Бюджеты** (синтетика): пересчёт проекции ≤ 200 мс на 10 млн провайдеров; сборка таблицы не медленнее Go;
   пиковая память не выше Go.

## Вне рамок

Приложение (команды, проекции, события), оболочки Tauri/dev-сервер, UI — это NG-D002+.

## Решения

- Собственный разбор плагинов вместо `esplugin`: тот под GPL-3.0 (ADR 0003).
- Тёплые структуры неизменяемы; проекция перезаписи — отдельный снимок, пересобираемый по приоритетам.

## Находки и риски

- **Ловушка прототипа Go:** несохранённый порядок молча применялся при открытии профиля (`pendingOrder`).
  Первая сверка дала 137 расхождений именно из-за этого — Go работал на другом порядке. Урок для NG-D002:
  отложенное намерение пользователя должно быть **видимым состоянием**, а не тихой подменой канона.
- **Память:** RSS процесса не равен живой памяти — освобождённые входные данные аллокатор не сразу отдаёт ОС.
  Для бюджетов меряем живую кучу таблицы (`ProviderTable::heap_bytes`) и пиковый RSS отдельно.
- **Интернер:** первая версия хранила каждое имя дважды (ключ в нижнем регистре + оригинал). Переход на общую
  арену строк + цепочки по хешу сократил сборку таблицы с 6,2 до 3,0–3,7 с и кучу до 718 МиБ на 9,4 млн провайдеров.
- **Риск:** холодный обход на этой машине 69,6 с против 64,2 с у Go (2 vCPU, файлы в page cache, ~1 млн чтений
  DDS-заголовков). В контракт не входил; разобрать в профилировании сканера (кандидаты: лишний `metadata()`
  на файл, порядок параллелизма между модами и внутри мода).
- **Проверено на реальных файлах сборки владельца** (`sat-cli inspect`, 2026-10-31): BSA v105 — 151 запись, сумма
  размеров сходится с файлом за вычетом оглавления; ESL — флаги, 4 мастера, автор и описание; записей 103, а HEDR
  говорит 140 = 103 записи + 37 групп (35 тем DIAL + 2 верхние) — счёт точный; DDS BC4 4×4 с 3 мипами = 24 байта,
  BC7 1024² = 1 048 576 байт (файл = данные + 148 байт заголовка). BA2 в сборке Skyrim нет — проверен только на фикстурах.
  Сами файлы модов в репозиторий не кладутся (чужая собственность).
- **После закрытия, первый прогон CI на Windows:** тест кеша сканера упал — нетронутая папка давала разные
  сигнатуры подряд. Причина: на Windows `DirEntry::metadata()` берётся из индекса родительской папки, который
  NTFS обновляет лениво. Сигнатура теперь читает метаданные по дескриптору (`std::fs::metadata`). Этот класс
  ошибок невидим на Linux — поэтому Windows-сборка в CI обязательна.
- **Первый прогон на реальной сборке (Windows, внешний SSD):** активный профиль — 1 118 модов, включён **0**,
  поэтому конфликтов 0 (поведение верное, отчёт — нет: молчал). Холодный скан 195 с на 185 тыс. файлов +
  516 тыс. записей архивов, из кеша 6,2 с. `sat-cli` теперь печатает профиль, корни модов, сколько папок на диске
  не упомянуто в modlist, предупреждает о нуле включённых и раскладывает время скана по фазам.
  На синтетике раскладка показала: чтение DDS-заголовков ≈ 61 % времени обхода, сигнатуры ≈ 14 % холодного
  прогона (считаются отдельным проходом, хотя обход читает те же метаданные) — кандидаты для NG-D002/профилирования.
- **Первый полный замер на сборке владельца** (Windows, внешний SSD, 4 логических ядра): 7 525 модов (1 789 включены),
  2,14 млн файлов + 2,38 млн записей архивов = 4,5 млн провайдеров, 3,64 млн путей; конфликтных путей 41 882,
  цепочек 1 505, контекстов 79, X = 99. Пересчёт проекции **51–96 мс**. Холодный скан **23,4 мин**: 90 % времени потоков —
  чтение 433 тыс. заголовков DDS (~9 мс каждый); из кеша **56 с** — почти целиком сигнатуры; сборка таблицы 7–13 с
  (на синтетике 1–2 с — разобрать: аллокатор Windows?). Причина главная: скан шёл на пуле по числу ядер (4), а работа
  ограничена диском. Сделан отдельный I/O-пул (`ScanOptions::io_threads`, по умолчанию 8 на ядро, не меньше 32;
  `sat-cli --io-threads N`). Дальше: подобрать N на машине владельца, удешевить сигнатуру, DDS-заголовки — ленивее.
- **С I/O-пулом 32:** холодный скан всех 7 525 модов **12,3 мин** (было 23,4 мин при 1 119 из кеша) — диск насыщен,
  среднее время DDS-заголовка 9 → 22 мс из-за очереди. Тёплый почти не изменился (56 → 47 с): сигнатура открывала
  дескриптор на каждый элемент (исправление NTFS выше) — это упор в стоимость системного вызова, а не в диск.
  Сигнатура v2: метаданные из листинга каталога (без открытия файлов); у каталогов хешируется только имя
  (их метки времени NTFS обновляет лениво), у файлов — размер и mtime. Записи кеша со старой сигнатурой
  принимаются один раз и перезаписываются, обновление не вызывает холодного прогона. На синтетике тёплый скан
  6,6 → 0,8–1,0 с. Аллокатор mimalloc в `sat-cli`: сборка таблицы −12 % на Linux; на Windows ждём замер.
- **Слабый ноутбук владельца:** тёплый прогон упал дважды — нехватка памяти (`memory allocation … failed`) и
  переполнение стека потока сканирования. Причины: все сырые факты сборки (4,5 млн записей) держались в памяти
  одновременно с таблицей; пул с перехватом задач кладёт обход одного мода поверх другого, и стандартных 2 МиБ стека
  не хватило на глубоких деревьях. Исправлено: `TableBuilder` + `scan_batched` (факты сворачиваются в таблицу пачками
  по 256 модов и выбрасываются), стек потоков сканирования 32 МиБ (резерв, не выделение), RSS печатается на всех ОС.
  Повторный замер на том же ноутбуке: падений нет; тёплый прогон **21–22 с** (на домашнем ПК было 47–56 с до
  сигнатуры v2), память **~460 МиБ** после всего, живая куча таблицы 297 МиБ на 4,5 млн провайдеров, пересчёт
  перезаписи 47–63 мс (разовый выброс 465 мс). Бюджет «старт из кеша < 10 с» ещё не выполнен: основное время —
  чтение и разбор 7 525 файлов кеша; кандидат — снимок таблицы целиком (Фаза 0, холодный ярус).
- Среда 2 vCPU: абсолютные времена на машине пользователя будут лучше, параллельные части масштабируются по ядрам.
